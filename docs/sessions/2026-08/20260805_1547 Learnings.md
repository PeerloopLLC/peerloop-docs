# Conv Learnings - 2026-08-05

## 1. Adopting a client's COLOUR must never mean inlining his HEX
**Topics:** design-tokens, merge-brian, testing

**Context:** The client's band colours (`#e3f1fc` / `#d3e7f8`) were adopted verbatim at his request, reversing a Conv-426 decision that had declined them.

**Learning:** The Conv-426 guard test asserted two separate things — "no raw hex from his branch survives" AND "the band uses `bg-primary-light`". Only the second was overturned. Keeping the hex loop intact while changing the token name preserved the invariant that actually mattered. When a guard test fails after a deliberate reversal, split its assertions: some encode the decision (invert them), others encode a discipline that survives the decision (keep them).

**Pattern:**
```js
// unchanged across the reversal — the discipline survives the decision
for (const raw of ['#e3f1fc', '#d3e7f8']) expect(html).not.toContain(raw)
// only this moved — it encoded the decision itself
expect(html).toContain('bg-primary-light')  →  expect(html).toContain('bg-brian-band')
```

## 2. A guard test written against another component drifts; one written against meaning does not
**Topics:** testing, design-system

**Context:** The same medallion assertion on `CommunityCatalogCard` was inverted twice inside one conversation — first to assert the treatment, then to assert its absence.

**Learning:** The churn was the signal. The test was implicitly asking "does this match the course card?", which is a question about another file and therefore unstable. Rewritten as "does NOT wear the course card medallion — the logo is this card's own subject", it encodes the *reason* and stops tracking a sibling's decisions. Repeated inversion of one assertion inside a single session is a reliable smell that the assertion is pointed at the wrong thing.

## 3. The same asset can carry two different meanings, and treatment must follow meaning not appearance
**Topics:** design-system, communities

**Context:** `communities.logo_url` renders on both the course card and the community card. Propagating the course card's medallion to the community card looked like a consistency win and was a semantic error.

**Learning:** On the course card the logo is a **foreign** entity — a seal bridging the cover→band seam that names another community, which is what justifies the overhang and the white ring. On the community card it is the card's **own** subject, with no seam to bridge. Identical asset, opposite meaning. Before propagating a visual treatment between surfaces, ask what the element *means* on each, not whether the two would look uniform.

## 4. Check the write paths before believing a field is supported
**Topics:** schema, communities, product-gaps

**Context:** The user asked for a task to replace the picsum placeholders and to check there was "a spot for these images and a way to store them".

**Learning:** `logo_url` and `cover_image_url` look symmetric in the schema and are not: the logo has a dedicated R2 upload endpoint with delete and an instant-managed settings control, while the cover is a **pasted URL in a text box** with no upload and no storage. That asymmetry is *why* the seed uses picsum URLs — a creator has nowhere to put a real cover. Same class as Conv 432's `primary_topic_id` finding: the read path looked fine and the write path was the defect.

## 5. A pre-Conv-423 branch's spacing classes may port 1:1 — check, don't assume either way
**Topics:** spacing, merge-brian

**Context:** The client's `CommunityBand.tsx` predates the Conv-423 spacing-base fix, so its class numbers could have meant 4× what they say.

**Learning:** Every number he used (`gap-8`, `px-24`, `py-8`, `sm:px-32`, `left-20`) was already among the ten `--spacing-N` names his branch overrode to literal px, so all resolved identically under our base and ported unchanged. The hazard is real but not universal — it applies only to numbers *outside* the overridden ten. Checking his `tokens-tailwind-bridge.css` for the override list took one command and removed the whole risk.

## 6. Verify a deploy from what the server actually serves
**Topics:** deployment, verification

**Context:** `wrangler deploy` printed "✨ Success", which only proves an upload happened.

**Learning:** Fetching the page's real stylesheet link and grepping the served CSS for the new token (`brian-band` × 10, both hexes present) proves the change reached users. The first probe returned empty; per the standing guard it was re-checked **out-of-band** with a different probe (download to file, `wc -c`, then grep) rather than re-running the same command — which is what produced the correct answer.
