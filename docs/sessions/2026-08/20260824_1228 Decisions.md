## 2. Remove the `/mod` admin-hide (sidebar gate → `isModerator || isAdmin`)
**Type:** Implementation
**Topics:** ui-ux, auth

**Trigger:** User: "why hide the moderator tab for admins… removed unless you can think of a good reason."

**Options Considered:**
1. Keep the design (Admin subsumes Moderation)
2. Relax the gate so admins also see `/mod` ← Chosen
3. View via a non-admin user

**Decision:** Both sidebar gates in `Sidebar.tsx` changed from `isModerator && !isAdmin` to `isModerator || isAdmin`.

**Rationale:** The only reason for the hide was redundancy with the admin console's Moderation Queue link (`AdminDashboard.tsx:75`) — weak. Admins have global moderation scope, so showing the link is correct. OR'd `isAdmin` (not a bare negation-drop) to match `requireModerationAccess`.

**Consequences:** Shipping-behavior change for ALL admins — they now see `/mod` in the sidebar as well as the admin console. Supersedes the Conv-254 MOD-NAV `!isAdmin` nav rule.

## 3. Course-moderator gap → RFC CD-041 (propose, don't build)
**Type:** Strategic
**Topics:** auth, docs-infra

**Trigger:** User: "We may need a course moderator role."

**Options Considered:**
1. Write it up as an RFC/task for review ← Chosen
2. Log as an observation only

**Decision:** Filed CD-041 (`docs/requirements/rfc/CD-041/`) with the two-tier moderation model, the gap analysis, two design options (extend community-mod scope vs a dedicated `course_moderators` table), 5 pre-implementation questions, and an 18-item staged checklist. Registered in RFC INDEX (Open); parked `[CRSMOD]` gated on the decisions.

**Rationale:** A real gap — community mods (Tier-2) govern their community's flagged content, not courses; courses aren't a moderated `content_type`; `can_moderate_courses` grants Tier-1 GLOBAL scope and is a misnomer. But it's a sizable feature needing design decisions first.

**Consequences:** New RFC folder + INDEX entry; parked task; nothing built.
