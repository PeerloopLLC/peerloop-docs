# Conv Decisions - 2026-08-10

## 1. Extract the shared rail shell rather than add a fourth hand-rolled copy
**Type:** Strategic
**Topics:** astro, docs-infra

**Trigger:** The client asked for the `/` + `/courses` right panel on `/course/{stub}`. Investigation found `/`, `/courses` and `/communities` each hand-roll the same ~18-line rail block — they only *mention* `ListingShell` in comments, having each replaced the centered shell to kill a dead left gutter.

**Options Considered:**
1. Bespoke copy on `/course` — fastest to show the client, adds a fourth copy and its drift risk
2. Extract the shell first, port `/course` onto it, migrate the other three after ← Chosen
3. Extract and migrate all four in one go — most durable, widest blast radius

**Decision:** Build `DiscoveryRailPanel.astro` + an `AppLayout` `right-panel` slot once; `/course` consumes it now, the three listing pages migrate in phase B.

**Rationale:** Four copies of one arrangement, free to drift, is precisely the `[CTA-HOST-GUARD]` problem Conv 434 had to unpick after it had already happened once. The client's request is the cheapest moment to collapse it rather than deepen it.

**Consequences:** Phase A shipped. Phase B is now the part that actually removes the drift risk — phase A only stopped it getting worse.

> **Insight:** A client request that duplicates an existing arrangement is the cheapest possible moment to consolidate it — the work is already funded and the blast radius is already being tested.

## 3. Pin the rail width on the course page instead of using the component default
**Type:** Implementation
**Topics:** astro

**Trigger:** With `lg:flex-1` on both, content and panel split 50/50 (466px each, measured) — a rail nearly twice the width of the one the client pointed at.

**Options Considered:**
1. Cap the course content at `max-w-[640px]` like the listing pages — large unrequested change to a content-rich page
2. Pin the rail to the measured reference width ← Chosen

**Decision:** `lg:w-[284px]` on this page; the component keeps `lg:flex-1` as its default.

**Rationale:** On the listing pages the rail is the *remainder* beside a 640px-capped column (measured 284px at ≥1440, 273 at 1280). The client wants the same panel, not the same content cap. Leaving the component default alone keeps phase B's migration of those three pages a visual no-op.

## 5. ALTER staging's one missing column rather than reseed
**Type:** Implementation
**Topics:** d1, deployment

**Trigger:** Staging was missing `enrollments.teaching_request_sent_at`; the user asked whether a reseed and a cron redeploy were needed.

**Options Considered:**
1. `ALTER TABLE ... ADD COLUMN` ← Chosen
2. Deploy only, skip the ALTER — ships code against a DB that will 500
3. Full reseed of staging — fixes it, wipes staging's data

**Decision:** One additive nullable column, then deploy. No reseed, no cron redeploy.

**Rationale:** Verified the *only* drift was that one column (689 vs 690 by name across 72 tables). Seed files last changed Conv 432, which staging already had, so a reseed would wipe data to solve nothing extra. Cron's newest deployment postdates its last code change.

**Consequences:** Staging schema now matches local exactly; staging is current at Conv 435 and verified live.

> **Insight:** "Do we need a reseed?" and "do we need a redeploy?" are both answerable from evidence — a name-level schema diff and a deployment-date-vs-last-code-change comparison — rather than from the reflex of doing both to be safe.
