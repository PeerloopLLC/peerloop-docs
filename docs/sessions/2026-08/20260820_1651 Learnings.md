# Conv Learnings - 2026-08-20

## 1. `eslint src/` exits 0 on warnings — a gate is silent about them
**Topics:** testing, cc-workflow

**Context:** codecheck reported `lint` PASS while 163 warnings existed; the user had seen the 163 by running eslint directly.

**Learning:** ESLint exits non-zero only on ERRORS. To surface/count warnings you must parse `-f json` structurally, not rely on the exit code. CI's `lint` step likewise passes on warnings — so warnings genuinely do not block a remote build.

---

## 2. spawnSync maxBuffer + stderr concatenation corrupt eslint JSON
**Topics:** cc-workflow, testing

**Context:** The reporter's ESLint block silently parsed 0 findings, then showed an unparseable blob.

**Learning:**
- (a) `spawnSync` default `maxBuffer` is 1 MB; ESLint's `json` formatter embeds each file's full **source**, so a real codebase overflows and truncates the JSON → bump to 64 MB.
- (b) Concatenating stderr onto stdout corrupts the JSON (ESLint writes noise to stderr) → parse **stdout only**.
- (c) An unparseable result must surface as a failure, never be swallowed as "no findings".

---

## 3. A `&&` chain can't be a reporter — it short-circuits
**Topics:** cc-workflow

**Context:** The first `codecheck` was `a && b && …`; a run stopped at the first failing gate and never reached the rest.

**Learning:** To "report on each type of issue" you need a runner that executes every check regardless of individual exit codes, collects results, and returns an aggregate — not a shell `&&` chain.

---

## 4. Porting inline checks to hard gates surfaces latent false positives ([CMH])
**Topics:** testing, cc-workflow

**Context:** The inline grep gates were advisory ("any output = review"); as hard CI-style gates they turned `verify` red on clean code.

**Learning:** Always calibrate a ported/tightened gate against the live clean codebase AND a planted violation. Two FPs surfaced: `locals.runtime` matching a JSDoc comment (fix: exclude comment lines like the datetime gate does); error-render not recognizing `if (error)` as a render (fix: add `if (error`/`error?.` to the handled-patterns).

---

## 5. check-tailwind-v4 `[--x]` value-ref vs `[--x:val]` property assignment
**Topics:** astro, cc-workflow

**Context:** `check:tailwind` flagged `lg:[--pin-top:68px]`, valid v4.

**Learning:** The v3→v4 change is only the variable-as-**value** shorthand (`bg-[--x]` → `bg-(--x)`). Arbitrary **property assignment** `[--x:val]` is valid v4. The colon distinguishes them — require a closing `]` right after the name (`\[--[a-zA-Z][a-zA-Z0-9-]*\]`) to flag only value-refs.

---

## 6. What blocks a "remote build" is defined by ci.yml, not intuition
**Topics:** deployment, cc-workflow

**Context:** Needed to categorize codecheck findings by whether they block a deploy.

**Learning:** `deploy:staging` = `npm run build && wrangler deploy`; the gating pipeline is `.github/workflows/ci.yml` (push/PR to main): lint(errors)·typecheck·astro·`lint:tz`·test·build all gate; E2E is `continue-on-error`. So the custom gates (tailwind/icons/tokens/…) and ESLint warnings are NOT build-blockers. `lint:tz` IS a CI gate — the `[TZLINT]` "orphan" was only local.

---

## 7. Full local seed = `npm run db:setup:local:feeds`
**Topics:** d1, cc-workflow

**Context:** Brian onboarding a new dev machine.

**Learning:** The `db:setup:local:*` scripts are a cumulative chain; `:feeds` is the superset (`:dev` ⊂ `:stripe` ⊂ `:booking` ⊂ `:feeds`). `:dev` (CLAUDE.md's "standard") omits Stripe + booking. Local uses miniflare — no `wrangler login` needed.
