# Conv Learnings - 2026-08-24

## 1. Seeded feed posts were invisible because the seed keyed Stream by slug, the app by entity id
**Topics:** stream, testing, dual-repo

**Context:** Verifying Jack's community feed rendered — it didn't, and neither did existing communities' seeded posts (only manually-UI-posted ones showed).

**Learning:** The feed API reads/writes Stream feeds by the ENTITY ID (`communities.id` = `comm-<slug>`, `courses.id` = `crs-<slug>`), but `scripts/seed-feeds.mjs` wrote Stream activities keyed by the SLUG. Slug ≠ id, so every seeded community/course feed post landed in a Stream feed the app never reads. The D1 `feed_activities.feed_id` correctly uses the slug (that's what the app's own POST + `recordFeedVisit` use for badges/visits) — the two systems deliberately key differently, and only the Stream write was wrong. Fix = map slug→entity id at the Stream write only.

**Pattern:** `streamFeedIdFor(post)` → `comm-`/`crs-` prefix for community/course, pass-through for a `streamFeedId` override (system/townhall = `'main'`).

## 2. A green gate can't reveal a latent bug — only a render check did
**Topics:** testing, stream

**Context:** All baseline gates were green, yet no seeded community feed had ever rendered.

**Learning:** The seed reported "26/26 activities created" and D1 rows were correct, so every automated signal was green — the defect only surfaced by actually loading the page and seeing an empty feed. Render/DOM verification catches integration gaps (external Stream keying) that unit/count assertions structurally cannot.

## 3. Data and static assets reach staging by different mechanisms
**Topics:** cloudflare, deployment

**Context:** User asked whether re-seeding staging without a deploy would break the code.

**Learning:** D1 data updates via seed commands (immediate, no deploy); `public/images/*` are part of the code build and only reach staging via a deploy. So seeding `avatar_url` to a local path that isn't deployed yields 404 broken images — never a code break. Concretely demonstrated with curl (`default-avatar.svg` 200 vs new avatar 404 pre-deploy).

---

## 4. Community teachers & role status are derived, not stored
**Topics:** d1, testing

**Context:** Adding a 2nd teacher + choosing sex-appropriate avatars.

**Learning:** No `is_teacher`/`is_creator` columns (derived from `teacher_certifications` + `courses`); the capability flag is `can_teach_courses`. Community teachers derive via `teacher_certifications → courses.progression_id → progressions.community_id` (member_role `'teacher'` retired Conv 120). No sex/gender column either — sex-correct avatars are just `avatar_url` choices, no schema change.
