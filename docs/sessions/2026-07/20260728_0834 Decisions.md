## 5. Reject SVG on community logo upload (N13)
**Type:** Implementation
**Topics:** security, r2, uploads

**Trigger:** His `ALLOWED_TYPES` includes `image/svg+xml`.

**Options Considered:**
1. Match his allowed types
2. Raster only ← Chosen

**Decision:** `image/jpeg`, `image/png`, `image/webp`, `image/gif` only.

**Rationale:** An SVG is an executable document (script, `foreignObject`), and these are served from our own origin by the N14 asset route — so an uploaded SVG would be same-origin active content. Our existing course-thumbnail endpoint already excludes SVG, so this also keeps the two consistent.

**Consequences:** Endpoint and the settings UI's `accept` attribute agree; a test pins the rejection.

## 6. Serve public assets through a prefix allowlist, not a bucket proxy (N14)
**Type:** Strategic
**Topics:** security, cloudflare, r2

**Trigger:** The route that fixes `[THUMB-404]` reads from a bucket that also holds private objects.

**Options Considered:**
1. Serve any key from the bucket
2. Allowlist the two world-readable prefixes, 404 everything else ← Chosen

**Decision:** `courses/*/thumbnail/` and `communities/*/logo/` only; traversal rejected; unknown prefixes answered identically to missing objects.

**Rationale:** Community resources, homework submissions and session recordings share the bucket and have their own auth-gated endpoints. A bucket proxy would silently bypass all of them.

**Consequences:** Verified live, not just in unit tests — with a real object seeded at `homework/sub-1/secret.pdf` the route still 404s, proving the allowlist gates *before* R2 is consulted so private-key existence is unobservable.

> **Insight:** One bucket with mixed sensitivity means the *route*, not the bucket, is the security boundary — and a deny path that answers identically to "not found" is what keeps the boundary from leaking existence.
