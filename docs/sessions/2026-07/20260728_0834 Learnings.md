# Conv Learnings - 2026-07-28

## 1. A "no route serves this" defect can hide indefinitely behind seed data
**Topics:** testing, cloudflare, r2, seeding

**Context:** Reading Brian's new `api/storage/[...key].ts` purely to disposition it. His docstring stated plainly that the upload endpoints "have always generated `/api/storage/{key}` URLs, but no route served them until now."

**Learning:** That was true on our branch too — `api/me/courses/[id]/thumbnail.ts:131` writes `/api/storage/{key}` into `courses.thumbnail_url`, and no `src/pages/api/storage/` directory existed. Every creator-uploaded thumbnail was a dead link. It survived because **dev and staging seeds use external `picsum.photos` URLs**, so the broken path is only reachable by performing a real upload — something no test and no seeded browse-through ever does.

**Pattern:**
When an endpoint *writes a URL* rather than returning bytes, the write path and the read path are separately testable and can be separately absent. Grep for who *serves* a stored URL shape, not just who produces it: `git grep "api/storage"` returned exactly one producer and zero consumers, which was the whole finding.

## 2. Reading a client's branch is a code-review of your own codebase
**Topics:** merge-brian, review-process

**Context:** §3 was scoped as "decide what of Brian's to adopt". Three of the findings turned out to be defects on our side, not design questions.

**Learning:** Two of the three §3 findings (F3 thumbnail 404, F4 Join/Leave dead on client-side nav) and part of the third (F5's 224px square) were **his observations about our shared ancestry**, not his inventions. His comments name them directly: *"clicked Join, feed still said join to participate"*, *"its w-56 hit the rem fallback and rendered 224px"*.

**Pattern:**
Treat a fork's bug-fix commits as a free audit. The fork author exercised paths we don't, so their fixes point at *our* untested seams. Worth capturing in the client-facing ledger too — it makes the document two-directional rather than a list of rejections.

## 3. Verify a plausible defect before fixing it, with a control
**Topics:** testing, astro, debugging

**Context:** F4 (Join/Leave dead after client-side navigation) was clearly plausible from the code — module scripts execute once per document and `ClientRouter` is active — but unmeasured.

**Learning:** Confirmed it with an explicit control rather than just observing the failure: the *same button on the same page for the same user* fires `POST /api/communities/q-system/join` and disables when reached by a hard load, and produces **zero requests** when reached by clicking through `/communities` → community A → `/communities` → community B. Without the control, "the button did nothing" could have been a permissions, hydration or seed artifact.

**Pattern:**
Patch `window.fetch` to record and *never settle* (`return new Promise(() => {})`) for the endpoint under test. That proves the handler fired without mutating state and without letting the code path reach `alert()`/`reload()` — which matters doubly in a browser-automation context where a modal dialog freezes the session.

## 4. jsdom silently collapses File bodies through a Request round-trip
**Topics:** testing, vitest

**Context:** The logo endpoint's 2MB size-cap test asserted 400 and got 200.

**Learning:** Under jsdom (this suite's global environment), a `File` put through `new Request(url, { body: formData })` and read back via `.formData()` returns with `size` reading **9** regardless of the input — while `type` and `name` survive, which is why every other assertion passed and only the size check failed. The cap was implemented correctly; the environment was lying.

**Pattern:**
When a handler only consumes `request.formData()`, hand it the `FormData` directly via a stub request instead of encoding a real multipart body. Probe before assuming a code bug: a 6-line throwaway test that asserts the observed value against a sentinel prints the real number instantly.

## 5. A shared primitive's new look should be an opt-in prop, not a fork
**Topics:** design-system, matt

**Context:** N9 — his branch replaced `CommunitiesRoleTabs`' use of the shared `RoleTabBar` with a bespoke inline pill row, and in doing so dropped the Matt role palette entirely ("Role colors intentionally dropped with the underline form").

**Learning:** The bespoke-row approach forces a choice between "match the new look" and "keep the shared behaviour". Adding `variant="pill"` to `RoleTabBar` gets the look while the primitive keeps owning the role palette, so `/courses` role tabs and `dev/primitives` stay byte-identical and the role colours survive for free.

**Pattern:**
Same shape as §1's SubNav adoptions and §2 M8 — when a client branch restyles a shared component in place, the adoption is usually "add an opt-in variant to the primitive", not "copy his markup into one consumer".

## 6. Aggregates must be filtered like the surface they summarise
**Topics:** d1, sql, loaders

**Context:** Porting his per-community `courseCount` / rating subqueries (N16).

**Learning:** His subqueries filtered only `co.is_active = 1`, while our `fetchCommunityProgressionsData` — which renders the actual Courses tab — filters `is_active = 1 AND is_archived = 0 AND deleted_at IS NULL` on a live progression. Ported as-is, a card could advertise "5 courses" for a community whose Courses tab lists 3. Also switched a flat `AVG(rating)` to review-count-weighted `SUM(rating × rating_count) / SUM(rating_count)`, so one 5.0-from-one-review course can't outrank fifty 4.6s.

**Pattern:**
A count on a card is a promise about a list somewhere else. Copy the *visibility predicate* from the loader that renders that list, not from the source branch. The test pins 4.61 and explicitly asserts *not* 4.80 — the number a flat mean would produce.

## 7. `entity-community` does not exist in our token system
**Topics:** design-system, matt, tokens

**Context:** His `CommunityCatalogCard` hero and `CommunityMiniHeader` roots both carry an `entity-community` class.

**Learning:** Our `tokens-semantic.css` defines `.entity-creator`, `.entity-student`, `.entity-student-teacher` and `.entity-course` — communities are **not** one of the five role entities, so `entity-community` is a no-op class on our side. Adopting it would have been the first step toward a community role palette, which sits right next to the per-community `accent_color` theming §1 M10 deliberately dropped.

**Pattern:**
A class name that reads like it belongs to a system is worth grepping for in that system's definition before copying it across.
