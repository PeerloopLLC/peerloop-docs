# Conv Learnings - 2026-07-26

## 1. A task's stated premise is a hypothesis, not a finding
**Topics:** process, verification, messaging

**Context:** `[CANMSG]`'s body offered two options, of which (a) "drop the client gate" rested on the claim that `canMessage` is near-vacuous under open messaging. That claim was written from reading `lib/messaging.ts`, which is true as far as it goes — the only non-vacuous input is whether the recipient is soft-deleted.

**Learning:** The premise held for the *logic* but not for the *data*. Three of the four surfaces rendering the hook did not exclude soft-deleted users, so dropping the gate would have been a real behaviour change rather than the no-op the task implied. Checking "can this input ever actually vary here?" per call site — rather than only reading the function — turned a rare-case regression into a clean removal, and incidentally exposed a latent dead-link defect (the members directory could link to a `/@handle` that 404s).

**Pattern:** Before deleting a guard as vacuous, enumerate its call sites and prove at each one that the guarded condition cannot arise. If it can, fix the source first; the guard then drops safely.

## 2. Prop-threading pressure is a design signal
**Topics:** react, component-design, messaging

**Context:** M4's task body said to thread `signedIn` through to 11 call sites. None of the 8 owning components knew anything about the viewer.

**Learning:** Needing to thread a value through many ignorant components usually means the value belongs to the leaf, not the callers. Making `signedIn` optional and resolving it from `useAuthStatus()` inside the island removed the boilerplate from 11 sites, kept the explicit prop for the two that genuinely know server-side (avoiding a flicker), and meant M5's 10 sites inherit the behaviour for free. The alternative — hardcoding `true` eleven times — would have been correct when written and silently wrong the first time one of those components was reused on a public page.

**Pattern:** An optional prop that falls back to a hook is strictly more useful than a required one when most call sites would pass a constant.

## 3. Changing a premise invalidates tests that encoded the old one implicitly
**Topics:** testing, react

**Context:** Making `signedIn` optional broke two pre-existing tests that had used *omission* of the prop to mean "signed out".

**Learning:** Those tests never failed for a bad reason — they failed because the meaning of omission changed underneath them. The right fix was to express "signed out" the way it now works (via auth status), not to re-add the prop to make the assertion pass. The same shape appeared in `useCanMessage.test.ts`, where the whole file had to be rewritten because "asks the API" was no longer a behaviour that existed.

**Pattern:** When a test breaks after a deliberate premise change, ask whether the test's *setup* encoded the old premise before touching its assertion.

## 4. A dev server that answers is not necessarily a healthy one
**Topics:** tooling, vite, dev-environment

**Context:** Mid-verification, `/teaching/sessions` returned 500 while the rest of the site was fine, on a dev server that had been running since the previous conv.

**Learning:** The error was a stale Vite dep-optimizer chunk (`node_modules/.vite/deps_ssr/react-chartjs-2.js?v=<hash>`) — adding imports across nine files triggered a re-optimize the long-running server couldn't follow. The distinguishing signature is that the **server responds** (not the `curl 000` of the already-known bricked-daemon variant) but a *specific* route 500s, while `npm run build` is clean. That last part is what proves it is never a code defect. Restarting also changes the bind: the fresh `astro dev` daemon listens on `[::1]` only, so `127.0.0.1` probes fail even though the server is healthy.

**Pattern:** Route-specific 500 + clean build + long-running dev server ⇒ `rm -rf node_modules/.vite` and restart; then use `localhost`, not `127.0.0.1`.

## 5. Reachability is a real limit on live verification, and worth naming precisely
**Topics:** verification, testing, process

**Context:** M4's done-test asked for per-site live verification of 11 affordances; 7 were reachable and 4 were not.

**Learning:** The four failures had distinct, nameable causes — two needed a three-step wizard state, one needed a live session, and one was gated on a `targetUser` that the single seeded `moderation_actions` row doesn't resolve. Recording *which* precondition each one needs is materially more useful than recording "4 unverified", because it converts an open-ended retry into a setup checklist. It also separates "couldn't reach" from "might be broken", which matters when deciding whether the gap is acceptable.

## 6. A consistency fix inherits its scope from the wrong set if you scope it to the caller
**Topics:** process, api, data-integrity

**Context:** `[CANMSG]`'s source-first fix (Learning 1) enumerated the surfaces *rendering the hook* and filtered those three loaders. The `/r-end` docs agent then found `GET /api/me/communities/[slug]/members` still unfiltered — a member-listing query that doesn't render the hook, so it was never in scope.

**Learning:** Enumerating call sites is the right move for deciding whether a guard is removable, but it is the wrong boundary for the fix that follows. "Every surface the guard reaches" and "every query that lists users" are different sets, and fixing only the first leaves the codebase *less* consistent than before — one query now visibly diverging from four rather than four agreeing on nothing. The give-away is that the resulting entry has to hedge its own title. Notably it took a second reader (the docs agent, working from the API docs rather than the diff) to see it.

**Pattern:** After a source-first fix, re-ask the question at the data layer — grep for the shape (`FROM users`, `JOIN users`), not for the caller — and check whether the fix created a new odd-one-out.
