# Conv Learnings - 2026-07-24

## 1. Playwright headless + dev-login is the reliable browser when the claude-in-chrome bridge can't reach the dev server
**Topics:** testing, cc-workflow, dual-repo

**Context:** Mid-conv the claude-in-chrome bridge's Chrome refused every connection to the local dev server (`ERR_CONNECTION_REFUSED`) on BOTH `127.0.0.1:4321` and `localhost:4321`, in a fresh tab — while `curl` got `200` on both. The bridge Chrome apparently routes loopback away (proxy), so it's structurally unable to hit this machine's dev server even though it reached the *user's* server earlier.

**Learning:** When the bridge can't reach the dev server, drive a **headless Playwright chromium** instead: `playwright` (1.59) + chromium are already installed; authenticate with `POST /api/auth/dev-login {email}` via `context.request.post` (sets the auth cookie in the context), then `page.setViewportSize` + `page.goto` + `page.evaluate`/`page.screenshot`. This gives DOM-truth measurement AND screenshots across exact widths, fully self-serve, and it faithfully reproduces the sidebar-collide (real viewport → real `lg:` sidebar toggle).

**Pattern:**
Script must run from inside `~/projects/Peerloop` (ESM resolves `playwright` from its node_modules; a scratchpad `.mjs` throws `ERR_MODULE_NOT_FOUND`). Write a temp `_hero-probe.mjs` at the repo root, run `node _hero-probe.mjs`, `rm` it after. Screenshots → session scratchpad. David = `david.r@example.com`.

## 2. The astro dev server binds IPv6 `[::1]` only by default → Chrome (IPv4) can't connect
**Topics:** cloudflare, astro, cc-workflow

**Context:** `lsof` showed the astro daemon listening on `TCP [::1]:4321` (IPv6 loopback only). `curl localhost` resolved to `::1` and worked; Chrome resolved `localhost`→`127.0.0.1` (IPv4) and got connection-refused. Relaunching with `npm run dev -- --host 127.0.0.1` bound IPv4 and both `curl` checks passed — but the bridge Chrome *still* refused (separate proxy issue), which is what pushed the switch to Playwright.

**Learning:** `--host 127.0.0.1` fixes IPv4/IPv6 mismatch for a normal browser; it did NOT fix the bridge (its problem is deeper — proxy routing loopback away). `astro dev` also runs as a **daemon** now (`astro dev stop` / `astro dev logs`), so server-side request/SSR logs go to `astro dev logs`, not the launch stdout.

## 3. Vite dep-optimizer cold-start churn masquerades as a wall of React errors
**Topics:** astro, testing

**Context:** The "many errors in the server console" the user flagged were `Invalid hook call` / `Cannot read null (useEffect/useState)` in Sidebar/NavDrawer/CurrentUserInit/CheckoutCancelToast — none of which this conv touched.

**Learning:** Root cause was a Vite dep re-optimization on cold start ("Re-optimizing dependencies because vite config has changed" ×3 → `Failed to fetch dynamically imported module: .vite/deps/audit-*.js` → React reloads mid-render → null internals). It **self-heals** once deps settle — a clean reload afterward has a clean browser console and clean `[200]` requests. This is the already-tracked [VITE-DEPS-WATCH]. `rm -rf node_modules/.vite` + restart clears it deterministically.

## 4. CourseHeader had a dead `enrolled` variant + stale doc; the size divergence was an M1 leftover, not design
**Topics:** navigation, matt

**Context:** The hero "goes very deep" complaint traced to the `scheduled` variant's `min-h-[360px]`, which the Conv-409 M1 compression left untouched while slimming only `default`.

**Learning:** `variant="enrolled"`/`headerHref` were referenced only inside `CourseHeader.tsx` — no call site passed them (dead code); the doc claiming `/success` used the enrolled variant was wrong. The three Figma frames legitimately differ in *content* (the scheduled next-session CTA) but were never meant to differ in *height*. Collapsing to one state-derived band removed the accidental divergence.

## 5. Container-query stacking can over-correct; shrink-to-wrap keeps a compact side-by-side
**Topics:** navigation, layout

**Context:** The container-query fix (`@container` + `@3xl:flex-row`) stopped the clipping but stacked the hero to 332px in a mid-width band (janky, non-monotonic across the sidebar-collide zone).

**Learning:** For a two-column band, the durable fix wasn't "stack when narrow" — it was to let the right column **shrink** (remove `shrink-0`) so its text WRAPS, keeping the hero side-by-side and compact (~198px) at essentially all tablet/desktop widths, and to stack only at true mobile (lower the container breakpoint to `@lg`). A `shrink-0` button inside the column sets the natural min-width floor, so the column shrinks to the button and the label wraps above it — no clip. Verified via Playwright that the deep-stack + the resize jank both disappeared. (The user's "wrap the label" instinct was right in spirit even though wrapping alone would not have reduced the stacked height.)
