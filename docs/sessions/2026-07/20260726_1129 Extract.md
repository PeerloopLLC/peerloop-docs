### 5. Exclude soft-deleted members from the creator's management list
**Type:** Implementation
**Topics:** messaging, api, data-integrity
**Trigger:** The `/r-end` docs agent reported that `GET /api/me/communities/[slug]/members` was the only member-listing query left without `deleted_at IS NULL` after this conv's `[CANMSG]` sweep — an inconsistency the sweep itself created. Raised at the pre-commit checkpoint; the user chose to act on it rather than defer.
**Options Considered:**
1. Add the filter for consistency with every other member surface ← **Chosen**
2. Keep it unfiltered and record why the management view deliberately differs
**Decision:** Add `AND u.deleted_at IS NULL` to the query, plus a test pinning it.
**Rationale:** The case for keeping it rested on the creator needing to see a deleted member's row in order to act on it. Reading the consumer settled that: `CommunityManagement.tsx` renders a **read-only** list — avatar, name, role badge, handle, joined date, and no row actions at all — so there is nothing to act on. Leaving it also made that panel's `Members (n)` count (derived from array length) disagree with the community Members tab, which now filters.
**Consequences:** Every member-listing surface now excludes soft-deleted users. `API-COMMUNITY.md` documents it on both the SSR endpoint note and the management endpoint's own section — replacing the divergence note the docs agent had written minutes earlier, which the fix made stale. Suite 6584.
