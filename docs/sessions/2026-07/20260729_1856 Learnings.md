# Conv Learnings - 2026-07-29

## 1. A cap must be measured in the unit the ranking function consumes
**Topics:** discovery, design, calibration

**Context:** The Conv-431 design specified "cap the tag count at ~5", calibrated from courses averaging 2.5 tags / max 3.

**Learning:** `lanes.ts` ranks For You by **distinct topic** overlap, not tag count — `overlapCount()` counts `item.topicIds`, and `compute.ts` builds that with `group_concat(DISTINCT tg.topic_id)`. So five tags inside one topic score `overlap = 1` and buy no rank at all; the exploit being defended against is topic *spread*, which a tag cap bounds only loosely. Resolving the same seed through `tags.topic_id` produced the number that actually mattered and was absent from the original calibration: **1.67 topics average, max 2**. Shipped as two caps because there are genuinely two payoffs at two granularities — `smart-feed/scoring.ts` scores at tag granularity while the rails score at topic granularity, so a single cap on either axis leaves the other open.

**Pattern:** Before calibrating a limit, find the expression that consumes the quantity and confirm the limit is denominated in the same unit. `MAX_ENTITY_TAGS` and `MAX_ENTITY_TOPICS` in `src/lib/entity-tags.ts`.

## 2. A column with no writer is worse than a missing column
**Topics:** schema, discovery, dead-code

**Context:** The plan asserted `/courses` was "merely degraded — its topic filter reads the same data, so a user can approximate the lane by hand".

**Learning:** `CoursesCatalog` filtered on `c.primary_topic_id`, whose **only writer anywhere in the repo was the dev seed**. Neither create endpoint set it (`api/me/courses/index.ts`, `api/admin/courses/index.ts` both omit it from their column lists) and no PATCH accepted it — so every course created through the product had it NULL and was permanently invisible to the topic filter, while the 6 seeded courses responded normally. A missing column fails loudly; a written-once-by-seed column produces a filter that demos perfectly and is broken for all real data. Conv 108 re-added it for exactly this filter and the rationale "all seed courses assigned a topic ID" was, in hindsight, the tell — that *was* the whole population.

**Pattern:** For any column a filter or ranking reads, grep the write paths, not just the read paths. Seed-only population is a silent-failure signature.

## 3. Checking consumers dissolved a "design decision" that was never open
**Topics:** design, precedent, investigation

**Context:** Open decision 5 in the plan — tag-level or topic-level storage for community tags — was recorded as "the first call in this design not settled by precedent".

**Learning:** All three existing surfaces already store tags and roll up to topics at read time (`user_tags` → `full.ts fetchInterestTopicIds`, `course_tags` → `compute.ts COURSE_COLS`, communities → the derived walk). Tag-level storage, topic-level reads, uniformly. `community_tags` is a literal third instance and no judgment call existed. The granularity question had teeth only for the *cap* and the *filter*, both of which are topic-level — which is what findings 1 and 2 turned out to be about.

**Pattern:** When a plan flags something as "the open decision", check whether the codebase already answers it before spending judgment on it. Third time in three convs that the biggest saver was checking whether the thing being asked for already existed.

## 4. Truncating the backfill is lossless *because* of the union
**Topics:** discovery, seeding, schema

**Context:** Materializing the derivation into `community_tags` produced 6 tags for `comm-ai-for-you`, one past the 5-tag cap.

**Learning:** The cap can bind on a backfill even when every contributing course is individually legal, because the derivation aggregates across all courses in the community (5 courses × 3 tags = 15). Truncating is safe here only because `compute.ts` still UNIONs the derived half at query time — verified on both local and staging D1, `ai-for-you` resolves all three topics from a 5-tag materialization that dropped `tag-049`. Only cold-start communities depend on the explicit half alone, which is the entire point of the table.

**Pattern:** System-chosen defaults truncate; user claims reject. Two functions, not one flag.

## 5. Round-robin, not prefix, when truncating a set whose value is its spread
**Topics:** algorithms, discovery

**Context:** Writing `capTagsPreservingTopics` for the backfill and the creation pre-seed.

**Learning:** A straight `slice(0, MAX_ENTITY_TAGS)` can spend the entire budget inside one topic and drop the entity's other topics — discarding exactly the signal the cap exists to protect. Taking one tag per topic before a second from any preserves the widest topic coverage that fits under both caps. The unit test pins this in both directions (`['a1','b1','c1','a2','a3']`, not `['a1'..'a5']`).

**Pattern:** When truncating a collection whose downstream value is diversity rather than count, interleave by the diversity key.

## 6. `COLLATE NOCASE` binds to the wrong thing under `IN`
**Topics:** sqlite, d1

**Context:** Replacing the old per-tag lookup (`WHERE slug = ? OR name = ? COLLATE NOCASE`) with a single batched query.

**Learning:** In `name = ? COLLATE NOCASE` the collation attaches to the `?` and the comparison works. In `name IN (...) COLLATE NOCASE` it attaches to the *result* of the `IN` expression, not the comparison — the correct form is `name COLLATE NOCASE IN (...)`. Used `lower()` on both sides instead: unambiguous, and the taxonomy is 55 rows so the lost index is irrelevant.

**Pattern:** Trailing `COLLATE` reads as if it applies to the comparison; under `IN` it does not.

## 7. SQLite has no LATERAL, so correlate at the top level
**Topics:** sqlite, d1, discovery

**Context:** Building the explicit ∪ derived topic expression for communities.

**Learning:** The natural shape — a scalar subquery over a nested `UNION` in the FROM clause — needs a correlated reference to `cm.id` from inside a FROM-clause subquery, which SQLite does not dependably support. Emitting two ordinary correlated scalar subqueries concatenated with `|| ',' ||` is valid, and the resulting leading/trailing/doubled commas and cross-source duplicates are handled by `parseTopicIdList`. Verified against real D1 (not just better-sqlite3): `system` yields `","` → `[]`.

**Pattern:** When a correlated FROM-subquery is tempting in SQLite, concatenate scalar subqueries and normalise in the application layer.

## 8. Same unscoped-selector error as last conv, caught by re-measuring
**Topics:** browser-verification, testing

**Context:** Live-checking the `/communities` topic filter; selecting a topic no community claims still showed all three.

**Learning:** `a[href^="/community/"]` was picking up `DiscoveryRailCard` links from the `lg:hidden` narrow-screen rails mount, which still hydrates at desktop width (`display:none`, not un-rendered — the Conv-431 finding). The filter was working the whole time. Scoping to `article[data-prov-name="CommunityCatalogCard"] h3 a` gave correct results immediately. Second conv running where a live reading looked like a defect and was the instrument.

**Pattern:** Scope DOM queries to the island under test via its `data-prov-name`, never a bare `href` prefix — this codebase renders the same entity in multiple simultaneously-hydrated islands.

## 9. A failing probe can be the most informative result
**Topics:** staging, schema-drift

**Context:** A staging probe errored with `no such column: payment_intent_id`.

**Learning:** The error revealed that staging had drifted from `0001_schema.sql` in a way unrelated to this conv's work — a third gap beyond the two I already knew about. That turned "should I ALTER or reset?" from a judgment call into a settled one: reset+migrate was the only option that fixes drift I hadn't enumerated.

**Pattern:** On a remote-environment probe, read the error rather than routing around it.

## 10. A shared library change can oblige a second deploy
**Topics:** deployment, cloudflare

**Context:** Deploying the staging worker after changing `compute.ts`.

**Learning:** `workers/cron/src/index.ts:13` imports `refreshDiscoveryRails` → `compute.ts`. Deploying only the main worker would have left the cron worker recomputing the cached rails blob every 15 minutes with code that doesn't know `community_tags` exists — the community half of For You would look broken on staging with no obvious cause, and the main worker's own code would be correct.

**Pattern:** After changing anything under `src/lib/`, check `workers/*/src/` for imports before assuming one deploy target.
