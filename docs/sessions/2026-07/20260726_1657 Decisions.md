# Conv Decisions - 2026-07-26

## 1. Icon sizing gets its own token axis, split three ways by role
**Type:** Strategic
**Topics:** css, design-system, accessibility

**Trigger:** User asked why `h-4 w-4` was replaced with `size-[16px]` on a 4px-based scale, then asked for a site-wide standard.

**Options Considered:**
1. Arbitrary `size-[Npx]` everywhere — unambiguous but permanently untokenized, and pinned against user font size
2. Reuse the spacing scale (`size-16`) — tokenized and rem, but cannot express 14/18/28 and keeps the N-vs-N×4 ambiguity
3. Dedicated icon-size tokens ← **Chosen**
4. Rename the `--spacing-*` override so no number can collide — cleanest, but touches all 4,711 spacing sites

**Decision:** `--icon-{12..64}` (rem) for standalone glyphs, `--icon-inline-{sm,md,lg}` (em) for icons beside text, fixed px for dots/avatars/hit-targets/component-defaults. Spacing keeps the numeric scale.

**Rationale:** There were **no icon-size tokens at all**, so the real choice was "wrong tokens vs no tokens", not "tokens vs arbitrary". The type scale is entirely rem, so a pinned icon beside growing text halves in relative size for the user who enlarged it. `em` beats `rem` for the inline family because it tracks the actual label rather than the document root.

**Consequences:** New token axis + bridge; 43 sites migrated; `05-color-and-tokens.md`'s never-implemented Conv-172 proposal marked superseded; ~2,000-site migration promoted to the ICON-SIZING PLAN block.

> **Insight:** When a category has no tokens at all, the argument "these tokens might be wrong" is not an argument for arbitrary values — it is an argument for naming what already ships and correcting the names later. The choice is only ever "wrong tokens vs no tokens".

## 2. Matt's Figma "Icon Size" collection is credited, not adopted wholesale
**Type:** Strategic
**Topics:** design-system, figma, provenance

**Trigger:** Found mid-build that Matt formalized icon sizes (Small 20 / Medium 24) — a designer source we had never used.

**Options Considered:**
1. Adopt only Matt's two values ← rejected
2. Numeric ladder with Matt's values flagged inside ← **Chosen**
3. Semantic `sm/md/lg` naming mirroring his modes

**Decision:** Eleven numeric steps; 20 and 24 marked `✓ Matt`, the other nine CC-owned.

**Rationale:** 16px is the most-used icon size in the app (72 sites) and is not in his set; 14/18/28 are also shipped and inexpressible on it. Adopting only Small/Medium would mean re-snapping shipped design rather than naming it. Mirrors how `--space-N` flags its four Matt-extracted values inside a scaffolded ladder, and how Conv 306/313 minted CC-owned `Button` variants.

**Consequences:** Doc section rewritten so the proposal and the implementation no longer contradict; reconcile if Matt returns.

## 3. Delete the dead marketing surface rather than park it
**Type:** Strategic
**Topics:** dead-code, tooling

**Trigger:** User: "We keep getting bitten by these public pages… replace their entire contents with Coming Soon."

**Options Considered:**
1. Stub the pages with "Coming Soon" — **already true**, so a no-op
2. Delete all 56 ← **Chosen**
3. Allowlist into `KNOWN_ORPHANS` and defer to `[RG-PUBLIC]`
4. Both

**Decision:** Deleted 80 files (56 components + 13 tests + 11 barrels).

**Rationale:** The bundler had been tree-shaking them out all along, so "keep until the redesign" bought nothing while costing recurring sweep collisions (twice documented). A fresh design will not reuse them (Conv 239 Matt phase-out). Git history is the recovery path.

**Consequences:** 334 → 278 components; orphan detector PASSes; knip unused files 0; `[ICON-TOK]` baseline −169; `[ORPHAN-BACKLOG]` Cat-B resolved; `[KNIP]` blocker (2) cleared.

> **Insight:** The user's stated problem ("these pages are hopelessly out of date") was already solved — the pages had rendered "Coming soon." stubs for a long time, and that stubbing is *why* the components behind them were orphaned. Checking whether the premise still holds turned a content task into a deletion task.

## 4. The bundler is the orphan oracle; knip does not replace route-reachability
**Type:** Implementation
**Topics:** tooling, dead-code

**Trigger:** User proposed knip for orphan detection; three oracles disagreed (14 / 53 / 56).

**Options Considered:**
1. knip `--include files` — 14, defeated by dead barrels
2. Route reachability — 53, zero false alarms but misses live-barrel cases
3. Sourcemap `sources` ← **Chosen as ground truth**

**Decision:** Sourcemap union is authoritative; the route detector stays as the cheap pre-sweep check; knip keeps unused-exports and dependency scope.

**Rationale:** Only the bundler resolves both barrel failure modes, because tree-shaking *is* the question. Name-matching minified `dist/` was tried and was wrong in both directions.

**Consequences:** `[KNIP]`'s "would replace `codecheck-orphan-components.mjs`" claim corrected; method recorded for re-runs.

## 5. Delete `GET /api/me/can-message/:userId`
**Type:** Implementation
**Topics:** api, messaging

**Trigger:** M6's explicitly deferred keep-or-delete call.

**Options Considered:**
1. Keep as a valid untested-by-UI surface
2. Delete ← **Chosen**

**Decision:** Removed endpoint + 7 tests; 6 docs updated.

**Rationale:** Zero `src/` callers since `[CANMSG]`; `canMessage()` in `lib/messaging.ts` was always the authoritative gate, so enforcement is untouched; `[KNIP]` would otherwise carry it as a permanent exception.

**Consequences:** `API-USERS.md`'s follow endpoint now *owns* the visitors-and-self-get-a-value convention it had been documented as mirroring.
