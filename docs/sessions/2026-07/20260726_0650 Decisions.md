# Conv Decisions - 2026-07-26

## 1. In-place composer via a shared opt-in island, not a per-page modal
**Type:** Implementation
**Topics:** ui, messages, components

**Trigger:** User reported that "Ask … a Question" on the course Peer Teachers and Meet the Creator tabs navigated away from the course page.

**Options Considered:**
1. Course page only — mount `NewConversationModal` directly in both tabs
2. Shared `MessageUserButton` island, adopted on the course page now, other sites opt in later ← Chosen
3. Leave the anchor as-is for consistency with the other 20 call sites

**Decision:** Build a shared island composing the existing `Button` + `NewConversationModal` + `showToast`, adopt it on the two course tabs, and leave every other call site untouched.

**Rationale:** Option 1 would create a second copy of the pattern immediately. A blanket site-wide flip was wrong because some sites (admin consoles, and the `SessionRoom` participant chip) legitimately want a full-page jump. Opt-in adoption matches the shared-primitive shape already used by the §1 Tier B work (`SubNav preserveScroll`, `SubNavItem dense`).

**Consequences:** New `src/components/messages/MessageUserButton.tsx`. `CreatorTab` prop `askHref` → `askUserId`. Signed-out viewers keep the `/messages?to=` anchor so the login bounce survives. Remaining 21 sites tracked as `[MSG-ICON]` + `[MSG-ADOPT-A]` + `[MSG-ADOPT-B]`.

## 2. Confirm before discarding an unsent message
**Type:** Implementation
**Topics:** ui, modals, messages

**Trigger:** User asked whether an outside click closes the modal or leaves it running; measurement showed it closes AND silently discards a typed draft.

**Options Considered:**
1. Keep the draft, keyed to recipient (CC's recommendation)
2. Block backdrop dismiss while text is present
3. Confirm before discarding, via the existing `ConfirmModal` ← Chosen
4. Leave as-is

**Decision:** Route every dismissal path (backdrop, Escape, ×) through a guard that raises a "Discard message?" `ConfirmModal` when `initialMessage` is non-empty.

**Rationale:** User chose the most protective option over CC's cheaper recommendation. It reuses an existing primitive and adds no new concept.

**Consequences:** Applies to `/messages` too, since it is the same modal — the message centre's composer gains the same protection. The send path calls `onClose` directly so it is never prompted. Two backdrops now stack at ~75% black (noted, cosmetic).

## 3. "Open in Messages" escape hatch — opt-in, not always shown
**Type:** Implementation
**Topics:** ui, messages, routing

**Trigger:** CC flagged that the composer has no thread history; user proposed a button that opens `/messages` with the recipient loaded.

**Options Considered:**
1. Opt-in via prop, off by default ← Chosen
2. Always shown (simpler, prop-less)
3. Fetch and show recent thread messages inside the modal
4. Drop the idea

**Decision:** Add `showOpenInMessages` (default OFF); only `MessageUserButton` opts in. Render as a real `<a href="/messages?to=…">`; leave modified clicks unguarded; route plain clicks with unsent text through the discard prompt.

**Rationale:** The same modal is mounted inside `MessagesCenter` on `/messages`, where the link would point at the current page — so always-on is circular. Verified `?to=` is already thread-aware (`MessagesCenter:104-110`), so the feature needed no new route, param or API. Anchor semantics preserve middle/cmd-click; those are safe to leave unguarded because the current page and draft survive them.

**Consequences:** The composer keeps the reader in place by default and offers a deliberate exit to full history. This substantially defuses the compose-blind concern that had made broad adoption look like a trade-off, and is why the sweep is worth revisiting.

## 4. Defer the 21-site adoption; sequence the work as a 6-step mini-plan
**Type:** Strategic
**Topics:** planning, messages, refactoring

**Trigger:** Sweep produced 21 modal candidates; user asked for a sequenced plan to finish the messages work.

**Options Considered:**
1. Adopt all 21 now
2. High-value 11 first
3. Only the 3 drop-in `Button` sites
4. Nothing yet — re-decide after the escape hatch ships ← Chosen

**Decision:** Park adoption; record a 6-step programme (M1 `[MSGBOOT]` → M2 `[CANMSG]` → M3 `[MSG-ICON]` → M4 `[MSG-ADOPT-A]` → M5 `[MSG-ADOPT-B]` → M6 `[MSG-CLEANUP]`) on the task board with dependencies and per-step done-tests. Execute M1 this conv.

**Rationale:** Two blockers made immediate adoption wrong: 19 of 21 sites need an icon variant that does not exist, and a live bootstrap bug meant the affordances did not render on a first visit at all — adopting on top of that would have been building on sand.

**Consequences:** `[MSG-INPLACE-ADOPT]` split into three tasks preserving the per-site dispositions. M1 completed this conv. M2 promoted to the head of the queue carrying a ⚠️ re-measure note, because M1 makes the per-row fan-out fire on every load rather than warm loads only.

## 5. Fix the bootstrap race in the consumers, not with SSR seeding
**Type:** Implementation
**Topics:** auth, react, current-user

**Trigger:** M1 execution; the task had proposed SSR-seeding the current user as the durable option.

**Options Considered:**
1. SSR-seed the user server-side (the task's stated "durable option")
2. Gate both consumers on the existing `authStatus` three-state ← Chosen
3. Timeout / retry workaround (explicitly ruled out in the task)

**Decision:** Have `MessagesCenter` and `useCanMessage` wait on `useAuthStatus()` before deciding, matching `StudentDashboard` / `ProgressionNudge` / `useCreatorGate`.

**Rationale:** The three-state signal already existed and was already the established pattern for exactly this problem. SSR seeding would have been new architecture solving a problem the codebase had already solved.

**Consequences:** Two-file fix rather than a rework. Both symptoms resolved and verified on fresh browser contexts. A genuine visitor is still redirected, so the fix waits for resolution rather than assuming a session.

> **Insight:** A nullable cached singleton is a two-state answer to a three-state question. The durable contract is not "seed it earlier" but "let consumers see `loading`" — every consumer that branches on `null` is a first-visit bug waiting to be reported as flakiness.
