# Conv Decisions - 2026-07-29

## 1. Skip Home for the narrow-screen mount
**Type:** Implementation
**Topics:** discovery, responsive, astro

**Trigger:** The user's requirement said "each page"; investigation showed Home differs.

**Options Considered:**
1. All three hosts
2. Courses + Communities ← **Chosen**
3. Courses only

**Decision:** Mount the narrow-screen rail on `/courses` and `/communities` only.

**Rationale:** `SmartFeed` already renders interest-matched `SuggestionCard`s from the *same* rails blob with no breakpoint gating anywhere in `SmartFeed.tsx` or `SuggestionCard.tsx`, so Home's mobile column already carries an interest-ranked entity surface. A second one would duplicate it in the same scroll.

**Consequences:** Home still gets the Recently Visited lane in its ≥lg aside (Phase 3), where it shows literal history rather than the `/communities` bridge.

## 2. `maxLanes` is a count, not a lane-kind filter
**Type:** Implementation
**Topics:** discovery, personalization

**Trigger:** The task body proposed "one For You lane (or `maxItems={2}`)".

**Options Considered:**
1. "For You only" filter
2. First-available, capped by count ← **Chosen**

**Decision:** Cap the number of lanes after building, keeping builder order.

**Rationale:** `lanes.ts:108` skips the For You lane entirely when the viewer has no interests, and visitors never have any — so a kind-filter would render an **empty** surface for every signed-out user, which is precisely the defect the mount exists to fix. First-available gives members For You and everyone else Trending. Verified live in both directions.

**Consequences:** The narrow mount is never empty for a viewer with any recommendable content.

## 3. No generic course lane on `/communities` — use the recency bridge instead
**Type:** Strategic
**Topics:** discovery, information-architecture

**Trigger:** User asked directly for an opinion.

**Options Considered:**
1. Generic course lane on `/communities`
2. Nothing
3. Recency bridge — parent communities of recently-visited courses ← **Chosen**

**Decision:** Keep `/communities` pure to its entity type; import the course signal only as parent communities.

**Rationale:** The aside is a narrow vertical column where every lane pushes the next below the fold, and Home already exists as the both-types surface. The bridge is the more coherent version of the same impulse: "you looked at a course, here's the community it lives in."

**Consequences:** If courses are ever wanted there for conversion reasons, make it contextual ("Courses in your communities") and place it last.

## 4. Visit history lives in localStorage as a denormalized snapshot
**Type:** Strategic
**Topics:** discovery, storage, architecture

**Trigger:** Phase 2 needed a store, and `feed_visits` was ruled out.

**Options Considered:**
1. localStorage + snapshot ← **Chosen**
2. D1 table + resolve endpoint
3. Both — localStorage mirrored to D1

**Decision:** Client-side store holding display fields captured at visit time.

**Rationale:** Decided by a constraint the plan had not named — every rail is built `LIMIT topN`, so the blob **cannot** render an arbitrary recently-visited entity; the snapshot removes the need for any lookup. And a server-only store would serve *fewer* people than the client one, since signed-out visitors browse the catalogs and would get nothing — structurally the same defect Phase 1 had just fixed.

**Consequences:** No new endpoint, no request, no schema. Costs cross-device continuity, addable later as a mirror without redesign.

> **Insight:** "Where should this live?" is often settled by a shape constraint elsewhere in the pipeline rather than by a storage-tier argument — here, `LIMIT topN` on the rail builder made the id-plus-lookup design unbuildable before any durability trade-off was weighed.

## 5. Recently Visited sits after For You
**Type:** Implementation
**Topics:** discovery, personalization

**Trigger:** Lane order interacts with the shipped `maxLanes={1}`.

**Options Considered:**
1. After For You ← **Chosen**
2. First (resume-first)
3. First, widening mobile to 2 lanes

**Decision:** Personalization leads; recency follows.

**Rationale:** With `maxLanes={1}` already shipped, a leading recency lane would mean the narrow mount **never** shows For You.

**Consequences:** Recency is systematically starved when For You claims the same entity — visible immediately in the small dev seed, less likely at production scale.

## 6. Removal is lane-scoped and time-based
**Type:** Implementation
**Topics:** discovery, ux

**Trigger:** User specified "remove ... from being shown again just because of the recency".

**Decision:** A removal stamps a time; an entry is hidden while `removedAt >= visitedAt`, so **re-visiting resurrects it**. The entity is never suppressed from For You / Trending.

**Rationale:** The user's phrasing scopes the suppression to the recency claim specifically. A fresh visit is a new statement of intent.

**Consequences:** A user cannot permanently ban an entity from the recency lane; visiting it again brings it back.

---

## 7. The remove control is deliberately NOT built on `ephemeral-dismiss`
**Type:** Implementation
**Topics:** discovery, dev-workflow

**Trigger:** The plan had recorded a caveat that removal would not persist in dev/staging.

**Decision:** Removal persists in every environment.

**Rationale:** `ephemeral-dismiss` suppresses persistence in dev/staging so QA sees all dismissible **chrome** on each load. Removing a row here is a **list edit** — an absent row is data, not hidden furniture.

**Consequences:** The previously-recorded caveat was wrong and was struck through in the plan.

## 8. Identity is `slug`, not `id`
**Type:** Implementation
**Topics:** discovery, data-modelling

**Trigger:** The course page's parent community object carries no `id`.

**Options Considered:**
1. Add `id` to the shared course loader
2. Key by slug ← **Chosen**

**Decision:** The recency store keys entities by slug, namespaced per entity type.

**Rationale:** Slug is in the URL on both entity pages, unique per entity type, and already what the rendered links use — and it avoided changing a shared SSR loader for a convenience feature.

**Consequences:** `visitKey(entityType, slug)` namespaces so a course and a community with the same slug never collide.

## 9. Creators are the primary but not the sole source of community tags
**Type:** Strategic
**Topics:** taxonomy, governance, discovery

**Trigger:** User asked whether creators should be sole source.

**Decision:** Creator-assigned, plus: **cap the tag count** (retrofitted onto courses), union with the derived roll-up, allow moderator edits, and give admins an override.

**Rationale:** The rails changed what a tag is worth — from a filing system the *user* pulls to a distribution channel the *platform* pushes — and `lanes.ts:124` ranks by overlap count, so claiming more topics ranks you higher. Courses are already sole-source with no cap, so the exploit is one API call and pre-dates this work. Cap calibrated from real usage (55 tags exist; courses average 2.5, max 3).

**Consequences:** Phase 4 (`[COMM-TOPICS]`) carries the cap as its non-negotiable item.

> **Insight:** A metadata field's governance requirements are set by its *consumers*, not by its schema — the same `tags` column needs no policing while only humans filter on it, and needs a cap the moment a ranker reads it.

## 10. Close the cross-island limitation rather than carry it
**Type:** Implementation
**Topics:** discovery, react

**Trigger:** User: "let's complete the issue you just reported last turn".

**Decision:** Added `subscribeRecentVisits()` + `notifyChange()` on all three mutators; removed the direct tick-bump so there is one path.

**Rationale:** The single-path shape also moved the `setState` into a subscription *callback*, which the `set-state-in-effect` lint rule explicitly permits — so lint held at its 164 baseline.

**Consequences:** Cross-tab sync was added in the same subscription function, beyond the reported issue; flagged to the user as an addition rather than folded in silently.
