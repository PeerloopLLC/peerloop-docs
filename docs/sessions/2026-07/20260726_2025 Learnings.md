# Conv Learnings - 2026-07-26

## 1. A guard rule that matches on component *name* will mistake a well-built primitive for a defect
**Topics:** tooling, icon-system, static-analysis

**Context:** `check-icon-sizing.ts` R2 flagged 46 "icons rendered with no size class". Reading them showed 14 were `entity/UserIcon` — an avatar with a typed `size?: 24 | 40` prop, which is a *better* API than a classname, and which the standard explicitly puts in the "keeps px" bucket.

**Learning:** `<(MattIcon|[A-Z]\w*Icon|[A-Z]\w*Logo)>` is a name test, not a semantic one. The better-designed the component, the more likely a name-based rule misreads it: an avatar with a size prop looks *identical* to an unsized icon from the call site. A rule about "is this sized?" must resolve the component, not the tag name.

**Pattern:** Detect self-sizing structurally rather than by allowlist, so the check can't rot as components are added:

```js
// A component qualifies if its definition body applies a dimension class or takes a `size` prop.
function selfSizingIcons(files) {
  const names = new Set();
  for (const file of files) {
    const defs = [...text.matchAll(ICON_DEF)].map(m => ({ name: m[1], start: m.index }));
    defs.forEach((def, i) => {
      const body = text.slice(def.start, defs[i + 1]?.start ?? text.length);
      if (HAS_SIZE.test(body) || /\bsize\s*[?:=]/.test(body)) names.add(def.name);
    });
  }
  return names;
}
```

## 2. The leverage in a classname migration is usually at the definition, not the call sites
**Topics:** icon-system, refactoring

**Context:** The tranche was framed as "46 call sites". Those call sites had no class *because their component supplied one* — so the thing actually deciding their rendered size was one line in each component.

**Learning:** 94 edits cleared 200 violations and corrected every un-classed usage site-wide, AdminNavbar's 17 among them, because `MattIcon.tsx:43` is upstream of all of them. When a census counts call sites, check whether a definition sits above them; the call-site count can be an artefact of where the scanner looked.

**Pattern:** Before migrating N call sites, ask what supplies the value when the call site omits it. Verify numerical identity before editing a default — `h-5 w-5` = `calc(0.25rem × 5)` = 1.25rem = `--icon-20` — so the change is provably neutral rather than hopefully neutral.

## 3. "No regression" from a route-walking scanner is not evidence about code that route-walking can't reach
**Topics:** testing, verification, icon-system

**Context:** `icons:scan` reported no regression after tranche 2, which would have read as verification. A direct probe showed only 4 of the 44 migrated sites had rendered at all.

**Learning:** The 44 were empty-state marks — they render only when a list is empty, and the scanner walks routes with seeded data. `/learning` measured identically before and after because nothing changed *there*. A green scan means "nothing I rendered got worse", which is a much weaker claim than "the change is verified", and the two are easy to conflate when the tranche and the scan are described in the same breath.

**Pattern:** After a migration, check whether the verifier actually observed the changed elements — count occurrences of the new token in the measured set — instead of trusting the pass/fail. Here that was: probe for `[class*="size-icon-"]`, measure at two root font sizes, and count how many grew.

## 4. A single `curl` distinguishes three different dev-server failures
**Topics:** dev-tooling, astro

**Context:** Fourth occurrence of `[DEVSRV-STALE]`; the diagnosis had been re-derived from scratch each time.

**Learning:** The three variants have disjoint signatures — `curl` returning `000` while `lsof` shows a bound port means a mid-run `npm install` bricked the module runner; an HTTP 500 naming a missing `deps_ssr/<dep>.js` means a stale Vite dep-optimizer cache; HTTP 200 with pre-flip content means the browser cache. `npm run build` staying clean is the tell that it is never the code. Also: `astro dev` has `stop`/`status`/`logs` subcommands, so teardown never needs `kill` against `lsof` output.

**Pattern:** Recorded in `memory/reference_devserver_stale_daemon.md` so the fourth diagnosis is the last one derived from scratch.

## 5. Reading a legacy component end-to-end shows the defect is systemic, not local
**Topics:** tailwind, legacy-migration

**Context:** `ModeratorInvite` was flagged for 4 icon classes. Reading the whole file showed 90 classes affected — skeleton loader bars at 8px and 4px, `space-y-4` button stacks at 4px, `p-4` alert boxes, `px-4` modal buttons.

**Learning:** When a component predates a global scale change, the icons are the *visible* symptom of a file-wide problem. Fixing only the flagged classes would have made it worse — a 32px glyph inside a container left at 16px overflows. The blast radius is worth measuring before deciding scope: here, only 7 files use the v3-era palette and only 2 carry overridden icon classes, which turned an open-ended worry into a bounded, one-off exception.
