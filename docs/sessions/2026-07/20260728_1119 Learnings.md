# Conv Learnings - 2026-07-28

## 1. A task's own framing can be the thing that's stale
**Topics:** process, investigation, memory-hygiene

**Context:** `[REC-REHOME]` had sat blocked across two convs on "destination undecided — Home is the obvious candidate but `[FEEDS]` bars panel surfaces on `/`". That sentence was written into the task body in Conv 425 and copied forward in Conv 426.

**Learning:** Every load-bearing clause in it was wrong or narrower than stated. `/feeds` (the memory's suggested destination) had been retired 96 convs earlier (Conv 331, `d47c8612`); the `[FEEDS]` bar named three specific composites in the *feed column* (FeedsHub / ActionCards / TriageStrip), not all panels on `/`; and Home already shipped an equivalent surface (`SuggestionCard` in `SmartFeed`, with a dismiss that trains future feeds). Verifying the task's stated blocker before accepting it took ~15 minutes and turned a "needs a product decision" item into a build.

**Pattern:** When a task has been carried forward unchanged across multiple convs with a stated blocker, treat the blocker as a claim to re-test, not a given. It was written when someone had less information than you do now. This is `[PREMISE]` (verify against consumers, not definitions) applied to the task board itself.

## 2. Grep the plan directory for an owner before designing a solution
**Topics:** process, planning

**Context:** Two mechanisms (MERGE-BRIAN §2 M4, §3 N8) were dispositioned across two separate walks, each spawning prerequisite framing, without either walk noticing that `plan/home-feed-merge/README.md` #34 `[RECO-UNIFY]` already scoped exactly this refactor — and that `src/lib/discovery-rails/types.ts` names the reco bands as its intended consumer in a comment.

**Learning:** The codebase pointed at its own answer twice — once in a plan file, once in a source header — and both walks missed it because they were reading *the client's branch* and *our current surfaces*, not our own backlog. The build got substantially easier once found: `lib/discovery-rails/client.ts` already had the cache + personalization lens, shipped Conv 261 with tests only.

**Pattern:** Before designing a surface, grep `plan/` and the relevant `lib/*/types.ts` headers for the feature noun. "Consumers (built later): …" comments are a designed hand-off that only works if someone looks.

## 3. Zero-cost personalization was already sitting in CurrentUser
**Topics:** architecture, performance, react

**Context:** The lane builder needs the viewer's topic interests. The obvious implementation is a fetch to `/api/me/onboarding-profile`, which returns `tags: [{tagId, topicId, …}]`.

**Learning:** `CurrentUser` already carries `interestTopicIds` with a `getInterestTopicIds()` getter, populated by `/api/me/full`. So the personalization lens costs **zero** additional requests — the same shape as Conv 418's `[CANMSG]`, which retired a 4-request-per-page fan-out by deriving from `useAuthStatus` + `useCurrentUser` instead of asking the server.

**Pattern:** Before adding a per-viewer fetch to an island, check `src/lib/current-user.ts` for the field. The singleton is stale-while-revalidate and version-polled, so reading it is both cheaper and fresher than a one-off fetch.

## 4. The three-state auth gate has now bitten three times
**Topics:** react, auth, bugs

**Context:** `[MSGBOOT]` (Conv 417) and `[COURSETAB-HASH]` (Conv 419) were both the same defect: a `client:load` island reading `useCurrentUser()` truthiness on its first render, when the cache hasn't hydrated, and treating that moment as "visitor".

**Learning:** The same trap was waiting here, with a quieter failure: no error, no bounce — just a member silently losing their For You lane on every cold load, in a surface nobody would think to test signed-in-after-hard-refresh. Gated on `useAuthStatus()`'s three-state from the start, holding the skeleton until *both* the blob and auth settle.

**Pattern:** Any island whose output differs for members vs visitors must gate on `useAuthStatus() === 'loading'`, not on user truthiness. The failure mode is silent degradation, not a crash, so it doesn't announce itself.

## 5. Predict from the data, then verify the render
**Topics:** testing, verification

**Context:** Verifying a personalized, ranked, deduplicated surface. "It looks right" is nearly worthless when the ordering is the feature.

**Learning:** Fetched the rails blob directly, computed by hand what marcus's For You lane *should* contain and in what order (`intro-to-n8n` at overlap 2, then five overlap-1 entities in global order), then read the DOM and compared. The match is evidence the ranking works; "four cards rendered" would not have been. The same prediction also called Trending's collapse, because its only item had already been claimed by For You.

**Pattern:** For any ranked/filtered/deduped surface, derive the expected output from the source data *before* looking at the render. It converts a smoke test into a falsifiable one, and it is the only way to catch an ordering bug that still produces plausible output.

## 6. A sticky container taller than the viewport hides its own content
**Topics:** css, ui

**Context:** The rail is `position: sticky; top: 24px`. Lane height is data-driven — lanes × items — and Home renders up to 8 lanes.

**Learning:** With the current small seed catalog Home already reaches 686px. On a real catalog the rail would exceed the viewport, and a sticky element taller than the viewport can never scroll to reveal its bottom. Found while measuring for something else; fixed with `max-h-[calc(100vh-48px)] overflow-y-auto` on all three hosts.

**Pattern:** Any `sticky` container whose height is data-driven needs a `max-h` + internal scroll. Don't size the decision on today's seed data.

## 7. Astro island children are a clean empty-state seam
**Topics:** astro, patterns

**Context:** The rail replaced a light-blue "coming soon" placeholder that is client-directed markup (Conv 298 `[HOME-RPANEL]`, and explicitly *kept* against the client's site-wide deletion in MERGE-BRIAN §2 M16). The island renders nothing when there's nothing to recommend — which would have left a genuinely empty box.

**Learning:** Passing the placeholder as Astro island **children** and rendering `{children}` in the null branch keeps the component host-independent (it knows nothing about blue panels) while preserving the client's markup byte-for-byte in exactly the case it was honest about. Verified: the placeholder renders at 284×200 with the original `rgb(239,246,255)`.

**Pattern:** When an island replaces existing markup that should survive as a fallback, pass the old markup as children rather than reimplementing it inside the component or leaving the host to guess which state rendered.

## 8. A probe can lie about the DOM if it walks the wrong way up
**Topics:** debugging, verification

**Context:** Checking the empty-state placeholder's background, an early probe reported `rgba(0,0,0,0)` — transparent — suggesting the blue had been lost.

**Learning:** The probe found the first element whose `textContent` matched, which was the `astro-island` wrapper, then called `closest('div')` and got the *sticky wrapper* (transparent) rather than the placeholder div. Dumping the actual subtree with computed styles showed the blue was correct all along. Two minutes from "found a defect" to "found a bad probe".

**Pattern:** When a DOM probe reports something surprising, dump the subtree before believing it. `textContent` matching hits every ancestor, and `closest()` from the wrong start node silently returns the wrong element.
