# Conv Decisions - 2026-07-26

## 1. Fix the data sources before removing the client-side messaging check
**Type:** Implementation
**Topics:** messaging, ssr, data-integrity

**Trigger:** Re-measuring `[CANMSG]` showed the per-row fan-out cost, but auditing the four call sites showed the gate was not vacuous on three of them.

**Options Considered:**
1. Drop the client gate outright — simplest, but renders a message affordance for soft-deleted users on three surfaces, failing only at POST
2. Add a batch endpoint over the existing `getMessageableFlags` — preserves behaviour exactly, but keeps a round-trip to compute `true` and needs the hook lifted out of `MemberRow`
3. Add `deleted_at IS NULL` to the three unfiltered loaders, then drop the gate ← **Chosen**

**Decision:** Add the missing `deleted_at` filters to `communities.ts` (member directory), `teachers.ts` and `creators.ts` (profile lookups), matching what `fetchPublicProfileData` already did, and only then make `useCanMessage` a local derivation.

**Rationale:** The filters are correct independently of messaging — `/@handle` already treated deleted users as not-found, so the other three were simply inconsistent with it, and the member directory was linking to a profile that 404s. Fixing the source made the removal provably equivalent rather than a rare-case regression, at the cost of three one-line SQL changes.

**Consequences:** Members lists and teacher/creator profiles no longer surface soft-deleted users. `useCanMessage` makes no network call in any state (4 requests → 0 on the measured page). `GET /api/me/can-message/:userId` is retained but has no UI caller; the keep-or-delete decision moved to `[MSG-CLEANUP]` (M6). A new test file pins the three filters precisely because the client derivation now depends on them.

## 2. `signedIn` resolves from auth status when the prop is omitted
**Type:** Implementation
**Topics:** react, component-design, messaging

**Trigger:** M4 required a `signedIn` value at 11 call sites across 8 components, none of which had any viewer knowledge.

**Options Considered:**
1. Hardcode `signedIn` at each of the 11 sites (all are authenticated-only surfaces)
2. Add `useCurrentUser()` / `useAuthStatus()` to each of the 8 component files
3. Make the prop optional and resolve it inside `MessageUserButton` ← **Chosen**

**Decision:** `signedIn` is now optional; when omitted it reads `useAuthStatus()`. An explicit prop still wins.

**Rationale:** Option 1 would have been right when written and wrong the first time a component was reused on a public surface — a constant that encodes an assumption nobody re-checks. Option 2 duplicates the same three lines eight times. Option 3 puts the knowledge in the one place that needs it, preserves the explicit prop for the two course tabs that know server-side (sparing them a resolve and a flicker), and means M5's 10 sites inherit it. This follows the `useAuthStatus` three-state pattern established in Conv 400/417 and already used by `StudentDashboard`, `ProgressionNudge` and `useCreatorGate`, so it is not a novel mechanism.

**Consequences:** While auth is unresolved the component renders the anchor, which is correct rather than merely safe — the anchor works for a signed-in viewer too, it just navigates. Two pre-existing tests that used prop omission to mean "signed out" were rewritten to say so via auth status.

## 3. `appearance` as a discriminated union rather than an options bag
**Type:** Implementation
**Topics:** react, typescript, component-design

**Trigger:** M3 needed a second trigger shape for `MessageUserButton` — icon-only, with the call site's own classes.

**Options Considered:**
1. A separate exported component (`MessageUserIconButton`) duplicating the modal wiring
2. Optional props on a flat interface, with runtime ambiguity about which combination is valid
3. `appearance: 'button' | 'bare'` as a discriminated prop union ← **Chosen**

**Decision:** One component, two appearances, typed as a union — `label` required in `'button'` mode, `title` required in `'bare'` mode.

**Rationale:** `Button` itself already uses exactly this shape (`LinkProps | NativeButtonProps`), so it follows an established codebase pattern rather than introducing one. It lets the type system enforce that the bare appearance is named — there is no visible label, so without `title` the control would be unnamed — instead of leaving that to review. A separate component would have duplicated the modal, discard guard and escape hatch, which is what the shared island exists to avoid.

**Consequences:** The bare trigger deliberately does not use the `Button` primitive; its pill radius, border and padding would fight the call site's styling, and preserving that styling is the point. It is also left unstamped for `data-prov`, so it adds no new `[PROV-SWEEP-DEBT2]` offender.

## 5. Exclude soft-deleted members from the creator's management list
**Type:** Implementation
**Topics:** messaging, api, data-integrity

**Trigger:** The `/r-end` docs agent reported that `GET /api/me/communities/[slug]/members` was the only member-listing query left without `deleted_at IS NULL` after this conv's `[CANMSG]` sweep — an inconsistency the sweep itself created, because it was scoped to the surfaces rendering the hook and this one does not. Raised at the pre-commit checkpoint; the user chose to act on it rather than defer.

**Options Considered:**
1. Add the filter, making it consistent with every other member surface ← **Chosen**
2. Leave it unfiltered and record why the management view deliberately differs

**Decision:** Add `AND u.deleted_at IS NULL` to the management query, plus a test pinning it (12 in that file).

**Rationale:** The case for option 2 rested on the creator needing to see a deleted member's row in order to act on it. Reading the consumer settled that: `CommunityManagement.tsx` renders a **read-only** list — avatar, name, role badge, handle, joined date, and no row actions at all — so there is nothing to act on. Leaving it also made that panel's `Members (n)` count (derived from array length) disagree with the community Members tab, which now filters.

**Consequences:** Every member-listing surface now excludes soft-deleted users, so the `[CANMSG]` entry's claim holds literally. `API-COMMUNITY.md` documents it on both the SSR endpoint note and the management endpoint's own section — replacing the divergence note the docs agent had written minutes earlier, which the fix made stale.
