# Conv Learnings - 2026-07-25

## 1. Brian's "many tab colours" = 4 hues inflated by elevation overhead
**Topics:** design-tokens, css, provenance

**Context:** User asked why the client-branch tab treatment has so many colours.

**Learning:** 10 raw values collapse to 4 hues (`#2a93d5` sheen, `#dfe6ee` border, `#0777b6` blue shadow, `#102a43` neutral shadow); the multiplier is a floating-elevation aesthetic — 2-layer shadows × {selected,default}×{rest,hover} × per-depth alpha ramps, plus shadows tinted to their surface (blue capsule → blue glow, white pill → neutral-dark shadow). A flat design needs ~1 colour per state (fill swap); elevation needs fill + border + multi-layer tinted shadow per state. None map to a design-system token → all land as raw "honest orphans," which is exactly why M7 left them behind in Conv 409.

## 2. Check the existing palette before adding "new" colours
**Topics:** design-tokens

**Context:** Adopting Brian's 4-colour palette into the style guide.

**Learning:** `#0777b6` (his blue shadow tint) is already `--americana-blue`/Primary-Default. Grepping the primitives before adding cut "4 new tokens" to 3. His gradient bottom (`to-primary-default`) and labels were already tokens — he only left raw the values with no token equivalent (sheen, elevation, pale border).

## 3. Tokenising raw colours is what makes adopting them prov-clean
**Topics:** provenance, design-tokens

**Context:** M7 (Conv 409) left Brian's colours behind because inline raw hex in a `@matt-source` primitive trips prov:sweep.

**Learning:** Adding the colours to the style guide as named tokens + having `SubNavItem` reference `var(--Tab-*)` keeps the primitive at **0 raw colour** → prov-clean. The user's instinct to "add to the style guide first" is precisely what dissolved the M7 objection. Registering the new `@matt-inspired` toggle in `matt-inspired-registry.ts` kept prov:sweep net-zero (LayoutToggle stays part of the pre-existing 9-err `[PROV-SWEEP-DEBT2]` debt).

## 4. Default-to-current-values CSS-var switch = zero-regression themeable primitive
**Topics:** css, refactor

**Context:** Making `SubNavItem`'s shared state ternary themeable without risking the default look.

**Learning:** Define the theme vars at `:root` to the *exact* prior utility values (`--Tab-Selected-Bg: var(--Primary-Light)` etc.), override under `[data-tab-theme='brian']`. Under the default theme the component renders byte-identically — verified live (Matt selected bg still `rgb(241,249,255)`). A shared-primitive change carries no default-path regression risk.

---

## 5. Piggyback the existing per-user SSR query; set the attribute server-side = FOUC-free
**Topics:** astro, ssr

**Context:** Applying the theme site-wide without a second DB round-trip or a flash.

**Learning:** `AppLayout` already runs one logged-in user query (for `nav_layout`); adding `tab_theme` to it costs nothing. Setting `data-tab-theme` on `<html>` at SSR (read from the DB column) is FOUC-free — better than `ThemeToggle`'s localStorage-on-mount approach (which has a documented flash). The client toggle flips the attribute live (no reload) and persists to the column, so the next SSR render carries the saved value across navigations + devices.

---

## 6. Local-D1 reset: reseed beats standalone `wrangler d1 execute` while the dev daemon is up
**Topics:** cloudflare, d1, testing

**Context:** Resetting a test user's `tab_theme` after live-verify.

**Learning:** Playwright `context.request.patch` didn't persist (the page-context fetch + UI clicks did); and standalone `npx wrangler d1 execute --local` failed "Workers runtime failed to start" because the running `astro dev` daemon held the local D1. Cleanest reset = `npm run db:setup:local:dev` (full reseed → all users back to the column DEFAULT).

---

## 7. The astro dev daemon persists across sessions and can serve stale content
**Topics:** cc-workflow, astro

**Context:** User saw an "old version" (`/matt` + `/discover` real) on 4321.

**Learning:** This project's `astro dev` runs as a **daemon** (`astro dev start/stop/status/logs`); `npm run dev` reported "already running (pid 9015)" from a prior session. A stale daemon (or the pre-flip worktree server, or Brave's localhost cache) can serve a months-old build on 4321. Verify current-ness deterministically via curl (`/matt`→404 proves post-flip code); tell the user to hard-refresh / private-window / use `127.0.0.1`.
