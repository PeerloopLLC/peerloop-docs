# Conv Decisions - 2026-07-29

## 1. Cap tag claims on two axes, not one
**Type:** Strategic
**Topics:** discovery, schema, abuse-prevention

**Trigger:** Investigation showed the Conv-431 single tag-count cap was denominated in a unit the ranking function does not consume.

**Options Considered:**
1. Topics only (~3) — bounds exactly what `lanes.ts` ranks on; leaves tag-granularity smart-feed over-claiming open
2. Tags only (~5), as originally planned — matches the existing spec; only loosely bounds topic spread
3. Both — `MAX_ENTITY_TAGS = 5` and `MAX_ENTITY_TOPICS = 3` ← **Chosen** (user selected)

**Decision:** Enforce both caps on every other-affecting tag write (`course_tags`, `community_tags`). Leave `user_tags` uncapped.

**Rationale:** Over-claiming has two independent payoffs at different granularities — the rails rank by distinct topic overlap, the smart feed scores per tag — so a cap on one axis leaves the other open. `user_tags` needs no cap because interests only change what that user sees; they are self-limiting. Both thresholds sit clear of measured usage (2.5 tags / 1.67 topics average; max 3 / 2).

**Consequences:** New `src/lib/entity-tags.ts` shared by both endpoints. The courses endpoint gains a cap it never had. A rejected claim now 400s before any write.

## 2. Remove `courses.primary_topic_id`, reversing Conv 108
**Type:** Strategic
**Topics:** schema, discovery

**Trigger:** Discovered the column has no writer outside the dev seed, so the `/courses` topic filter never matched an in-product course.

**Options Considered:**
1. Fix it now, in this task — repoint both catalogs at the `course_tags` roll-up and retire the column ← **Chosen** (user selected)
2. Own task after Phase 4 — build `/communities` on the roll-up now, log a `[CODE]` for `/courses`; pages stay inconsistent meanwhile
3. Log it only, change nothing

**Decision:** Removed the column; `/courses` and `/creators` loaders now emit `topic_ids` from the `course_tags` → `tags` → `topics` roll-up, and both catalogs match *any* claimed topic.

**Rationale:** Same code shape `/communities` needed anyway, so doing it here gave the new filter a correct pattern to copy rather than a broken one. Leaving it would have shipped a second catalog filter modelled on a dead signal.

**Consequences:** 11 source files and 6 test fixtures touched. Conv 108's decision-log entry marked SUPERSEDED with the reason its rationale held only for seed data. Live: `/courses` `top-014` now returns 5 courses, two of which have different old primaries.

## 3. Union explicit community tags with the derived roll-up
**Type:** Implementation
**Topics:** discovery, schema

**Trigger:** Phase 4 design; needed to decide whether explicit tags replace or supplement the progressions→courses→tags derivation.

**Options Considered:**
1. Explicit overrides derived — simpler, but goes stale silently as tags rot
2. Derived only — the status quo; has the cold-start hole
3. Union both ← **Chosen**

**Decision:** `COMMUNITY_COLS` emits `COALESCE(explicit,'') || ',' || COALESCE(derived,'')`, deduped in `parseTopicIdList`.

**Rationale:** A community genuinely does relate to its courses' topics, and the derived half self-corrects when explicit tags rot; the explicit half closes the cold-start hole. Also makes backfill truncation lossless.

**Consequences:** Two concatenated correlated subqueries rather than a nested UNION (no LATERAL in SQLite). Dedupe became load-bearing — a duplicate would inflate `overlapCount`.

## 4. Widen the tag editor set to moderators and admins — tags only
**Type:** Implementation
**Topics:** authz, communities

**Trigger:** Phase 4 called for moderator-editable tags; the PATCH endpoint was creator-only.

**Options Considered:**
1. Keep creator-only, consistent with the rest of the endpoint
2. Widen the whole endpoint to moderators
3. Widen for `tags` only, leaving settings creator-only ← **Chosen**

**Decision:** New `canEditCommunityTags` helper mirroring the two tiers in `lib/auth/moderation.ts` (global admin/moderator from JWT; community-scoped active `community_moderators` row). Settings stay creator-only.

**Rationale:** A community has no single accountable author, unlike a course, and a creator who drifts away shouldn't freeze a wrong tag set. Widening rename/archive was not asked for and carries different risk.

**Consequences:** Body parsing moved before the authz decision, since the gate now depends on which fields are touched. `requireModerationAccess` deliberately not reused — it redirects unauthenticated callers to `/login` rather than answering 401.

## 5. Restore staging by reset+reseed at the feeds level
**Type:** Implementation
**Topics:** staging, deployment, d1

**Trigger:** User asked to deploy and seed staging; the conv dropped a column, which `[D1-SCHEMA-REMOTE]` cannot patch onto a migrated remote D1.

**Options Considered:**
1. `ALTER TABLE` the delta onto staging — impossible for a dropped column, and would miss unenumerated drift
2. `db:setup:staging:dev` — base seed only
3. `db:setup:staging:feeds` — reset + migrate + dev + stripe + booking + feeds ← **Chosen**

**Decision:** Full reset at the deepest seed level, after verifying all 11 staging users are seed-recreatable.

**Rationale:** A probe error revealed a third schema gap (`enrollments.payment_intent_id`) predating this conv, so only a reset fixes drift I hadn't enumerated. Staging was already at the feeds level — `:dev` would have silently dropped the booking-test user and 21 feed activities. R2 is untouched by a D1 reset, so the 6 resource blobs survived.

**Consequences:** Staging D1 rebuilt; `community_tags` 12 rows; `primary_topic_id` gone. Both `peerloop-staging` and `peerloop-cron-staging` redeployed.
