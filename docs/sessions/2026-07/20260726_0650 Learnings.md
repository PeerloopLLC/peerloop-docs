# Conv Learnings - 2026-07-26

## 1. A three-state auth signal existed; the bug was consumers ignoring it
**Topics:** auth, react, current-user

**Context:** `[MSGBOOT]` was filed with a fix direction of "SSR-seed the user, or add a loading state" — implying new architecture.

**Learning:** `src/lib/current-user.ts` already exports `AuthStatus = 'loading' | 'authenticated' | 'visitor' | 'session_expired' | 'error'`, a `useAuthStatus()` hook (a `useSyncExternalStore` mirror), and `subscribeToAuthStatusChange`. `StudentDashboard`, `ProgressionNudge` and `useCreatorGate` already gate on `if (authStatus === 'loading') return;`. The messages consumers simply read the nullable `getCurrentUser()` singleton instead. The fix was two files joining an existing pattern — no new architecture.

**Pattern:** Before designing a state mechanism, grep the module that owns the state for existing exports. A nullable getter and a status enum often coexist, and the bug is usually that a consumer picked the wrong one.

## 2. A nullable singleton conflates "unresolved" with "absent" — and the failure is silent
**Topics:** auth, react, ssr

**Context:** `getCurrentUser()` hydrates from localStorage first, then revalidates from the API. On a browser with no prior visit it returns `null` until `CurrentUserInit` resolves.

**Learning:** Two independent consumers both read that `null` as "logged out". `MessagesCenter` redirected to `/login` (which bounced an authenticated user to Home); `useCanMessage` set `canMessage=false` without even calling the API, so every `{canMessage && …}` affordance rendered nothing. Neither failure logs anything — the page just quietly does the wrong thing, and both self-heal on the second visit, which is exactly why they survived this long.

**Pattern:** Any cached-then-revalidated singleton needs a tri-state consumer contract. A nullable getter cannot express "not yet known", and every consumer that treats `null` as a decision is a latent first-visit bug.

## 3. Cold-vs-warm is a distinct test axis that a warm browser cannot reveal
**Topics:** testing, browser, playwright

**Context:** Both `[MSGBOOT]` symptoms were only found by probing with a **fresh** Playwright context (empty localStorage) and comparing against a second load in the same context.

**Learning:** Repeated loads in one browser context are not independent samples — the first load populates the cache that hides the bug from every subsequent load. The measurements (`cold 0 icons / warm 5 icons`; `cold load 1 → /`, `cold load 2 → /messages`) only exist because each probe used `browser.newContext()`.

**Pattern:** When verifying anything that reads a client cache, make first-visit an explicit case: `await browser.newContext()` per probe, never `page.goto()` twice in one context.

## 4. Verification scripts have their own race conditions
**Topics:** testing, playwright

**Context:** The first live verification reported the Creator tab failing to preselect the recipient (🔴), while the Teachers tab passed.

**Learning:** The assertion ran immediately after the modal title appeared, but the preselect is an async fetch fired on open — the check was racing it, and the two tabs simply lost the race differently. Probing the API directly showed it returned the creator correctly. Re-running with `waitFor({state:'visible'})` showed both tabs passing.

**Pattern:** A failing verification is a claim about the *test* as much as the code. Before reporting a product bug from a probe, confirm the probe waits on the thing it asserts — especially where an effect fires a fetch on mount.

## 5. Reading call sites beats pattern-matching them
**Topics:** refactoring, code-search

**Context:** The sweep began as `grep "messages?to="` → 22 hits, which looked like a 22-line href swap.

**Learning:** Reading each site showed only 3 are `Button` components; the other 19 are bespoke icon-only `<a>` tags with per-site classNames, sizes and hover colours. The shared island renders a `Button`, so it does not drop into 19 of them. Reading `AdminDetailPanel.tsx` separately overturned an assumption stated earlier in the same conv — the admin sites are slide-over panels, not standalone pages, which inverted their disposition.

**Pattern:** For a "swap N call sites" estimate, read the call sites. Grep gives the count; only reading gives the shape, and the shape is what determines whether the work is one commit or three tasks.

## 6. Two 50%-opacity backdrops stack
**Topics:** ui, modals

**Context:** `ConfirmModal` renders over `NewConversationModal`; both are `fixed inset-0 z-50` with their own `bg-black/50`.

**Learning:** Equal z-index means later-in-DOM wins, so placing `<ConfirmModal>` after `</Modal>` stacks correctly without touching z-indices. But the two backdrops compose to ~75% black, so the page reads noticeably darker while the prompt is up. Legible, just heavier than intended.

**Pattern:** When nesting modal primitives that each own a backdrop, decide deliberately whether the inner one should suppress its own.

## 7. `@container` creates a containing block for `position: fixed`
**Topics:** css, modals

**Context:** Before mounting a modal inside a course tab, checked whether any ancestor would trap it.

**Learning:** `container-type: inline-size` establishes a containing block for fixed-position descendants — so a `@container` ancestor would have clipped the modal to the container rather than the viewport. The only `@container` in `src/` is on `CourseHeader`'s `<header>` (Conv 413 `[HERO]`), which is a sibling of the tab body, not an ancestor. `overflow-clip` on the teacher card was harmless by contrast.

**Pattern:** Before mounting a `position: fixed` overlay inside page content, grep for `@container` / `container-type` / `transform` / `filter` on the ancestor chain — any of them silently changes what "fixed" means.
