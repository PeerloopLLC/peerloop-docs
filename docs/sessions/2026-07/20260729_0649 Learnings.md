# Conv Learnings - 2026-07-29

## 1. A recorded blocker is a claim; test it against the tool, not the description
**Topics:** process, premise-testing, tooling

**Context:** `[DEVSRV-KILL]` asked for a script to "capture the spawned PID and kill only that". `[DEVSRV-STALE]` recorded one variant as "never fully root-caused".

**Learning:** Both dissolved on contact with the actual tool. `astro dev --help` showed `stop`/`status`/`--ignore-lock`, and the lock file (`.astro/dev.json`, recording `{pid, port, url, background, startedAt}`) made the requested script unnecessary. The "unpinned" variant was a one-command trap discoverable in about two minutes. This is the fourth consecutive conv where re-testing a recorded blocker collapsed it — consistent with `[PREMISE]`.

**Pattern:** Before building what a task asks for, run the tool's `--help` and read its lock/state files. The feature may already exist.

## 2. Guarding a dangerous command is the cheap part; it survives elsewhere
**Topics:** process, guards, tooling

**Context:** Added a hook rule blocking `lsof` + `kill` after measuring that `lsof -ti:PORT` returns the browser's pid.

**Learning:** The pattern survived in **four** other places — a memory file actively instructing it, two code-repo scripts embodying it, and a decisions doc recording it as an adopted convention. One of them was telling the assistant to run the exact command the new hook escalates.

**Pattern:** After adding a guard, grep the whole dual-repo for the guarded pattern. A guard that contradicts standing guidance produces friction, not safety.

## 3. Dead code can be the last holder of a correct model
**Topics:** refactoring, code-review, deletion

**Context:** `CourseCreatedCard` had zero consumers and zero tests; the static comparison against `CreatorStudio`'s `CourseCard` supported immediate deletion.

**Learning:** It implemented a correct three-state course status that **both live surfaces lacked**. Deleting it on "who calls it?" would have discarded a model that became a shipped defect fix. The right question for dead code is what it *knows*, not who calls it.

**Pattern:** Before deleting an unreferenced component, diff its behaviour against the live component that replaced it. Fields it has and the live one lacks are candidate defects in the live one.

## 4. A green gate conceals drift as effectively as a red one — and nothing prompts a look
**Topics:** gates, tooling, provenance

**Context:** `prov:sweep` reported "consistent" while 8 registry entries pointed at deleted files, accumulated across six convs over ~two months.

**Learning:** Conv 428 established that *a red gate cannot detect a new offender*. This is the inverse and arguably worse: a red gate at least nags. These rows were only found by tripping over them while deleting an unrelated component.

**Pattern:** For any registry↔filesystem gate, check both directions. The sweep already did a proper bijection for icons (SVG ↔ registry) — the component side had only half of it.

## 5. Diagnose by reading the implementation, not by reasoning from the symptom
**Topics:** debugging, process

**Context:** Logged `[PROV-DANGLE]` as "the sweep is one-directional" based on the symptom.

**Learning:** Wrong. The sweep *does* existence-check one array (`COMPONENT_CANDIDATES`, clean at 0 of 22); the defect was asymmetry between two arrays that look interchangeable — `PHASE6_EXTRAPOLATION_CANDIDATES` (46 entries) was only ever read for its *paths*, never validated, and held all 8 dangling entries. The symptom was consistent with both explanations, and only reading `prov-sweep.ts` distinguished them — which also made the fix smaller and better targeted.

**Pattern:** When a gate misses something, read the gate before writing the task describing why.

## 6. Verify a display defect by driving the exact broken state
**Topics:** testing, verification

**Context:** The retired-status defect could not be reproduced from seed data — all 6 local courses were `is_active=1/is_retired=0`.

**Learning:** Setting `is_retired=1` while deliberately **leaving `is_active=1`** produced the precise previously-broken combination and made the before/after unambiguous. Picking the orthogonal case, not just any retired course, is what made the check decisive.

**Pattern:** When two flags are independent, drive the combination that distinguishes the fix — not the common case.

---

## 7. `lsof -ti:PORT` is not "the server"
**Topics:** tooling, dev-server

**Context:** Measured while verifying dev-server teardown.

**Learning:** It returns every process holding a *connection* on that port, including browser client sockets, and those linger in CLOSE_WAIT after the server dies. `lsof -iTCP:PORT -sTCP:LISTEN -t` returns only the listener — verified to match astro's own lock pid exactly while excluding a deliberately-held client.

**Pattern:** Port-liveness checks must be LISTEN-scoped. Anything else conflates clients with servers.
