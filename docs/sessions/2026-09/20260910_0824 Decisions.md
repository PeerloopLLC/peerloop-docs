# Conv Decisions - 2026-09-10

## 1. Peerloop-native columns, not strict Dataview parity
**Type:** Implementation
**Topics:** obsidian, billing, skills

**Trigger:** SPT keeps `Channel/Who/Via/Slack` for merge-parity with the Obsidian `project-time-report3` exports; Peerloop coding cards never populate those.

**Options Considered:**
1. Strict `project-time-report3` column parity (merge with Obsidian meeting/slack TSVs)
2. Peerloop-native columns: `Date, Focus, Start, End, Adjust, Hours, Bill?, Convs, Blocks` ← Chosen

**Decision:** Default to Peerloop-native columns; surfaced the tradeoff to the user (parity is a `rBlockReport.columns` config edit if ever wanted).

**Rationale:** Peerloop coding is standalone billing, not a merge-into-Obsidian-exports workflow; the Slack/meeting columns would always empty-drop, and Convs/Blocks are the useful Peerloop dimensions.

**Consequences:** Report reflects the real Peerloop card; parity remains reachable via config without a code change.

## 2. Hours from the `Billable` field
**Type:** Implementation
**Topics:** obsidian, billing

**Trigger:** SPT recomputes Hours; Peerloop has an authoritative slot-rounded `Billable`.

**Options Considered:**
1. Recompute End−Start+Adjust (SPT parity)
2. Parse `Billable`, fall back to the computed value ← Chosen

**Decision:** `Hours` = `billableToHours(Billable)` with a Start/End/Adjust fallback.

**Rationale:** `Billable` is what Peerloop actually bills (slot-rounded, overflow-capped); recomputing would diverge.

**Consequences:** Report totals match the vault's own billed time.
