# Conv Learnings - 2026-09-27

## 1. The guard scans the command string, not the invocation — quoted danger-phrases self-trip it
**Topics:** cc-workflow, guards

**Context:** A self-test that piped danger-strings (`git push --force`, `git push -f`) through the hook for regex matching itself became a Bash tool call whose *own* command text contained those phrases; the PreToolUse guard matched and prompted for confirmation, even though nothing was executed.

**Learning:** `guard-dangerous-bash.sh` is a pure string matcher over `.tool_input.command` — it cannot tell an executed command from a quoted argument. Two consequences: (a) any self-test / demo whose text contains a guarded phrase will trip the guard on the outer call; (b) the Conv-458 scoping fix narrows *one* false-positive class (unrelated `-f` elsewhere in a compound command) but does not touch this deeper data-vs-command class, which would need real shell parsing. When self-testing a guard, route the danger-strings through a file or base64 so the tool-call text is inert, or warn the user a prompt is expected.

## 2. Scope a multi-token danger to a single command segment with `[^;|&]*`
**Topics:** cc-workflow, guards

**Context:** The force-push rule checked for `git push` and a force flag independently over the whole string, so `git push` batched with an unrelated `rm -f` false-fired.

**Learning:** To require two tokens to belong to the *same* invocation, chain them in one regex with `[^;|&]*` between (matches any run of chars that are not a command separator). Because grep is line-oriented, `[^;|&]` also cannot cross a newline — so the segment scope holds across both `;`/`|`/`&` and multi-line commands, with no loss of real coverage.

**Pattern:**
```
…push\b[^;|&]*(--force\b|--force-with-lease\b|[[:space:]]-f([[:space:]]|$))
```
