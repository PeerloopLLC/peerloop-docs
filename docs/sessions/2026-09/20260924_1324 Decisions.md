# Conv Decisions - 2026-09-24

## 1. Auto-certify the creator as the course's first teacher, in the backend
**Type:** Implementation
**Topics:** api, courses

**Trigger:** A published-but-teacherless course is un-enrollable (checkout rejects `no_teachers`) — a visible dead end; the client (Brian) wants creators to be teachers automatically.

**Options Considered:**
1. Backend — INSERT the cert in `POST /api/me/courses` ← Chosen
2. Client — auto-fire the existing self-cert POST in the create success handler

**Decision:** Backend INSERT right after the course INSERT (mirrors `isCreatorSelfCert`), + enable `can_teach_courses`.

**Rationale:** Authoritative (can't be skipped by a non-UI caller), one write, no extra round-trip. Verified safe: the course is a draft (`is_active=0`) at creation, so it's invisible + un-bookable until published — auto-cert can't expose a half-built course.

**Consequences:** New courses always have a teacher; catalog/rails gate passes them once published; the explicit self-cert flow (UI panel, PLATO steps) becomes a re-activation / discover path.

## 2. Teacher removal = reuse existing controls + opt-out UI + last-teacher guard (option C)
**Type:** Implementation
**Topics:** api, courses

**Trigger:** Auto-cert makes "creator steps down from teaching" a common need; the existing PUT-deactivate had no strand-protection guard.

**Options Considered:**
1. A — reuse existing deactivate/revoke as-is
2. B — + a clear creator-row opt-out control
3. C — B + a last-active-teacher guard ← Chosen

**Decision:** Keep the studio deactivate/revoke; add a "You" marker + "Stop teaching"/"Teach again" toggle (with confirm) on the creator's own row; add a backend guard blocking deactivation of the only active teacher of a published course with active enrollments.

**Rationale:** No new mechanism needed; the guard closes the gap that DELETE already covered but PUT-deactivate didn't (stranding enrolled students).

**Consequences:** New guard + 2 regression tests; UI opt-out symmetric to the auto opt-in.
