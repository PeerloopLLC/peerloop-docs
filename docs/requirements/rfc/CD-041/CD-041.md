# CD-041: Course-Level Content Moderation (Course-Moderator Role)

**Date:** 2026-08-24
**Source:** Surfaced by Fraser during Conv 441 while investigating the community-moderator role (part of the FIXES-AUG-21 batch — see [original.txt](./original.txt))
**Type:** New feature / architecture gap — moderation model extension
**Client:** Brian (relayed by Fraser)
**Status:** Open — **proposal for review, not yet approved to build**

---

## Purpose

While wiring up an every-role test user (`Jack Elam`) and relaxing the Sidebar's
`/mod` gate for admins, we investigated what a **community moderator** actually
governs — and found a real gap the client's instinct named: **there is no
course-level content moderation, and no course-moderator role.**

This document captures the current model, the gap, and a proposed design **for
review before any build.** No schema or code changes are implied by this RFC's
existence — the checklist in [RFC.md](./RFC.md) is gated behind the
Pre-Implementation decisions below.

---

## Current moderation model (as-built)

Two-tier, defined in `src/lib/auth/moderation.ts`:

| Tier | Who | Scope | Elevated actions (warn/suspend)? |
|------|-----|-------|-----------------------------------|
| **1 — global** | `is_admin`, or the `can_moderate_courses` flag (→ JWT `moderator` role) | ALL flags, every community | ✅ Yes (`canPerformElevatedAction` = global-only) |
| **2 — community** | active row in `community_moderators` | flags whose `community_id` is in their community list | ❌ No |

**What is moderatable:** `content_flags.content_type ∈ { 'post', 'comment', 'profile' }`,
each carrying a nullable `community_id`. So moderation targets **community
discussion content (posts/comments) and profiles** — scoped by community.

## The gap

1. **Courses are not a moderated content type at all.** No `content_flags` row can
   point at a course review, a course discussion-feed post, a homework submission,
   or course Q&A. Course-level content has **no moderation path**.
2. **`can_moderate_courses` is a misnomer.** Despite the name, it grants Tier-1
   *global* content moderation — nothing course-scoped.
3. **Community moderators do NOT monitor courses.** They are scoped to their
   community's discussion content, not the courses that belong to that community
   (courses attach to a community via `progression → community`).

So the answer to the client's question — *"are community moderators supposed to
monitor all courses in that community?"* — is **no, and today nobody does.**

---

## Design options (the fork to decide)

**Option A — Extend community-moderator scope to course content.**
A course belongs to exactly one community (via its progression). Make a community
moderator's scope also cover **course content for courses in their community**.
- No new moderator table.
- Still requires new `content_flags` course content types + a `course_id` column.
- Simple mental model: "you moderate everything in your community, courses included."
- Downside: no per-course granularity (can't appoint a mod for one course only).

**Option B — Dedicated `course_moderators` table (per-course role).**
A new table mirroring `community_moderators`, granting a **course-scoped** tier.
- Per-course granularity; a creator can appoint a mod for a single course.
- More work: new table, a third `ModerationScope` variant, appointment UI/API.
- Downside: more moving parts; overlaps conceptually with community moderation.

**Recommendation:** start from **Option A** (least new surface, answers the client's
actual question directly), and only add Option B's per-course table if per-course
granularity is genuinely needed. Both share the same `content_flags` schema work.

## Pre-Implementation questions (must answer before build)

1. **Which course content is moderatable?** Course reviews · discussion-feed posts
   (`discussion_feed_enabled` courses) · homework submissions · Q&A — which of these?
2. **Option A or B?** Extend community-mod scope to course content, or a dedicated
   per-course `course_moderators` table?
3. **Who appoints course moderators?** (If Option B) — the course creator, admins,
   or both? (Community mods are appointed by the community creator today.)
4. **Role label + Sidebar:** does a course moderator get the "Moderator" role label
   (`roles.ts userRoles`) and the `/mod` Sidebar item? Today the label reads
   `can_moderate_courses`; a course-scoped mod (no flag) wouldn't qualify without a change.
5. **Rename `can_moderate_courses`?** It is a global-scope flag misnamed as
   course-scoped. Rename to e.g. `is_platform_moderator` / `can_moderate_content`,
   or keep-and-document? (Rename touches auth/session, roles, seed, admin UI.)
